# Tasks — Dependency-Ordered Breakdown

Turn an **implementation plan** into an ordered, dependency-aware task list mapped to pipeline stages — so `/schema` → `/code` → `/wire` execute against a concrete checklist. Sits between `/plan` and `/schema`. Resumable; skippable for trivial work.

## Usage

- `/tasks #42` — breakdown from issue number
- `/tasks billing` — breakdown from feature name
- `/tasks billing hogwarts` — product-scoped

## Argument: $ARGUMENTS

## Instructions

### 1. READ — Load the plan

```bash
gh issue view <N> --repo <repo> --comments
```

Require an `## Implementation Plan` comment (from `/plan`). If missing, stop and route back to `/plan`. Extract: pattern choices, architecture decisions, mirror target, file plan (from the spec).

### 2. DECOMPOSE — Order the work

Break the plan into atomic tasks, each:

- mapped to its pipeline stage (`schema`, `code`, `wire`, `check`)
- tagged with the lane that runs it, from `engine.json → lanes`: `[build]` for implementation with a known pattern (most schema, code and wire tasks), `[judge]` for a decision or a review (a migration on live tenants, an auth boundary, the final verify), `[lookup]` for finding where something lives, `[script]` for a step that is one command (`pnpm tsc --noEmit`, a generator)
- ordered so dependencies come first (schema before actions before UI)
- carrying its own verify step (the stage's exit gate)

The tag is how the work is dispatched later: a `[build]` task goes to a build agent with a written brief (sonnet, medium), a `[judge]` task stays in the main loop or goes to an opus specialist, a `[lookup]` goes to Explore, a `[script]` runs without a model. Tag by the work, not by how important the feature is.

Use `.claude/templates/tasks.md` as the shape.

### 3. PUBLISH — Write the checklist to the issue

```bash
gh issue comment <N> --repo <repo> --body "<task breakdown>"
```

Header `## Task Breakdown`, render as a GitHub checklist (`- [ ] [build] …`) grouped by stage so progress is trackable on the issue. End with `*Generated by tasks stage. Ready for implementation.*`.

### 4. EXIT GATE

Task-breakdown comment exists on the issue: every task mapped to a stage, tagged with a lane, ordered by dependency, each with a verify step. Ready for `/schema`.

## When to skip

A one- or two-file change doesn't need a breakdown — go straight to `/schema` or `/code`. The pipeline is a menu, not a mandate.
