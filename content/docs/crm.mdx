# CRM

Databayt runs a self-hosted **[Twenty](https://twenty.com)** fork ([databayt/twenty](https://github.com/databayt/twenty), branch `databayt`) with **one workspace per product**. Every team member has **one login that works on all workspaces** — sign in once on any link, then move between them with the **workspace switcher (top-left)**.

| Product | URL | Pipeline |
| ------- | --- | -------- |
| **Hogwarts** | [hogwarts.databayt.org](https://hogwarts.databayt.org) | School leads — 3,206 rows, the [scrape](/docs/scrape) and [funnel](/docs/funnel) lanes both work this one |
| **Mkan** | [mkan.databayt.org](https://mkan.databayt.org) | Property hosts and listings |

| **Moallimee** | [moallimee.databayt.org](https://moallimee.databayt.org) | Pre-launch prospects |

The old `*.crm.databayt.org` hosts still resolve but 307-redirect to the same path on `<product>.databayt.org`. The default landing host is `app.databayt.org`.

> **`mkan.databayt.org` is the CRM, not the mkan app.** The app is `mk.databayt.org`, migrating to `mkan.sd`. A script that mints an outreach or claim link must never default to the CRM host. These names also collide with hogwarts' tenant wildcard, which provisions schools at `<domain>.databayt.org` — guarded by `hogwarts/src/lib/reserved-subdomains.ts`.

## Topology

| Piece | Where |
| ----- | ----- |
| **Frontend** | Twenty's React SPA on Vercel |
| **Backend** | `twenty-server` + `twenty-worker` + `postgres:16` + `redis`, in Docker **on Abdout's Mac**, host port **3100** |
| **Public API** | Tailscale Funnel — `https://twenty-api-2.tail42a5c4.ts.net` |
| **Version** | pinned `v2.31.1` (upstream is ~v2.30 on its own numbering; the fork's checkout is v2.17) |

> **The CRM is down whenever the laptop is.** Every scheduled CRM job is a Mac job — which is why the funnel's cadence clock runs on launchd and Vercel cron rather than a Twenty `CRON` workflow. The worker must be up too: webhooks, crons and the workflow engine all run through BullMQ.

## API access

**REST + metadata API only.** Never `psql` into a workspace schema: the REST surface is what the in-progress `packages/twenty-api` rewrite preserves, and raw SQL skips search vectors, timeline and activity. There is deliberately **no Twenty MCP** configured — turning it on means changing a pinned, restore-verified backend, and the scripts cost zero tokens as they are.

```bash
export TWENTY_API_URL=http://localhost:3100   # NEVER 3000 — that is hogwarts' dev server
export TWENTY_API_KEY=$(security find-generic-password -s databayt-twenty -a hogwarts -w)
```

Tokens live in the macOS Keychain under service `databayt-twenty`, account = workspace name. They are signed with `APP_SECRET`, so moving hosts with a different secret invalidates all four. Limits: 100 requests/minute, 60 records per batch call.

Defaulting to port 3000 is not hypothetical — it answers `307` on `/graphql`, which is why the Hermes CRM crons silently returned nothing for weeks while reporting `last_status: ok`.

## Webhooks

Both products receive real-time events from their workspace. Registered 2026-08-18 and
verified end to end against production, not just configured:

| Workspace | Target | Operations |
| --- | --- | --- |
| **hogwarts** | `ed.databayt.org/api/webhooks/twenty` | `company.updated`, `opportunity.updated` |
| **mkan** | `mk.databayt.org/api/webhooks/twenty` | `home.updated`, `host.updated`, `opportunity.updated` |

Twenty signs each delivery with `X-Twenty-Webhook-Signature` — an HMAC-SHA256 over
`` `${timestamp}:${body}` `` — **not** an `Authorization` bearer, and the secret is stripped
from the payload before signing, so verification must run against the raw request text.
Secrets are per-product and live only in Vercel; a receiver with none configured refuses
every delivery rather than accepting it.

Three properties worth designing around: **5-second timeout, no retries, and private IPs are
SSRF-blocked.** So a receiver must ack fast and do its slow work elsewhere, a dropped event
is gone for good, and local development needs a tunnel rather than `localhost`.

> **A 200 is not proof of anything.** mkan's receiver answered 200 for every delivery for
> months while processing none of them — it read fields Twenty does not send, so every branch
> fell through. Both ends reported success the entire time. hogwarts' receiver therefore
> stores a durable row and keeps `received` and `applied` as separate, separately observable
> facts.

## Backups

`twenty/scripts/backup-twenty.sh`, launchd `com.databayt.twenty-backup`, daily 03:30. It dumps Postgres **and** tars the storage volume — `STORAGE_TYPE=local`, so attachments are not in the database and a SQL-only dump would silently lose them. Lands in `~/backups/twenty` (14 days) and Google Drive (30 days).
