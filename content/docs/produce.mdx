# Produce

`produce` turns a request into a finished, approved video. It is a **ledger**, not a renderer: it
creates the project folder, records each of the 14 stages, holds the human gates and ships the
approved master to the CDN. The work of each stage belongs to a skill that already exists
([draft](/docs/social), [record](/docs/record), [higgs](/docs/media), [edit](/docs/edit) and the
rest) — `produce` chains them and re-implements none.

## The three lines

| Line | Makes |
| --- | --- |
| `hogwarts` | Product explainers and tutorials, real UI |
| `mkan` | Marketplace intro, property storytelling |
| `databayt` | Company, people, engineering |

## Quick start

```bash
P="node ~/.claude/skills/produce/scripts/produce.mjs"
$P init --brand hogwarts --identity balqalam --category introduction --subject main --lang ar,en \
  --audience "School owners and principals" --objective "Book a 1-month free trial"
$P status <ID>
$P advance <ID> <stage> --file <deliverable> [--variant sa-ar]
$P approve <ID> --version V001 --by <login> [--gate script|look|version|publish]
$P ship <ID> --dry-run
```

| --- | --- | --- | --- |
| 01 | request | `01-brief/request.json` | `produce init` |

| 03 | brief | `01-brief/creative-brief.md` | draft voice doctrine |
| 04 | script | `03-script/script.md` | draft, Arabic first — **gate 1** |
| 05 | storyboard | `04-storyboard/shot-list.json` | schema-validated |
| 06 | assets | `05-assets/asset-manifest.json` | reuse first, then shoot / record / generate |
| 07 | visual | `06-production/visual-manifest.json` | record, blender, higgs, HyperFrames — **gate 2** |
| 08 | audio | `07-audio/audio-package.json` | voice, music bed, loudness |
| 09 | edit | `06-production/editing/edit-project.json` | edit, FilmCraft, captions |
| 10 | render | `08-render/masters/master.mp4` + delivery cuts | encode, poster, VTT |
| 11 | qa | `09-quality/qa-report.md` | media-qa agent — must pass |
| 12 | approval | approval record | human — **gate 3** |
| 13 | cdn | `10-publishing/manifest.json` | `produce ship` |
| 14 | publish | `10-publishing/publishing-record.md` | publish + facebook — **gate 4** |

## The four human gates

A gate is a point where the work stops until a person says yes. Each is recorded with
`approve --gate <name>`, in this order:

1. **Script sign-off** (`script`) — light, before the expensive stages (visual, audio, edit, render refuse without it, and refuse again without a lock; see [Lock the line](#lock-the-line)).
2. **Look approval** (`look`) — after the visual stage: a person reviews the film's look, the keyframes or the animatic. Machine shows it as waiting until it is approved. `produce` records the approval and does not block a later stage on it.
3. **Exact-version approval** (`version`) — tied to one `Vnnn` and the sha of its master. A re-render voids it.
4. **Publish approval** (`publish`) — a separate yes that names the destination. Approving a version is not approving a post.

Hard rules: real product UI only for product claims; generated scenes are illustrative; no publish without approve.

## One film issue and its work orders

A film is tracked on GitHub by **one film issue**. Every piece that a person does is **its own work
order**: a separate issue with one request, for one person, with one deliverable. The film issue
lists them all, so a film is no longer a single issue with a checklist and nothing else.

Nothing reaches GitHub by accident. Each command below prints a **draft** first: what it would
create, upload or post. Only `--create` writes. When a film plan is accepted in Machine, the
Video department's lead runs these commands itself: the film issue first, then a work order for
each piece the plan gives to another person.

```bash
$P issue <ID>                                              # draft of the film issue
$P issue <ID> --create                                     # create it once
$P order <ID> <formula> --to <login> --set scene="…"            # draft of a work order
$P order <ID> <formula> --to <login> --set scene="…" --create   # upload its references and create it
$P submit <issue> <file>…                                  # draft: the uploads and the receipt
```

| Command | What it does |
| --- | --- |
| `issue <ID>` | Prints the film issue: the brief, the versions with their predicted links, the 14 stages as a checklist ticked from the ledger, the four gates (script, look, version, publish), and a line for every work order |
| `issue <ID> --create` | Creates it in `databayt/kun` (or the repo given with `--repo`) and stores it in `project.json`. When it exists, `--create` or `--sync` rewrites its body from the current state |
| `order <ID> <formula> --to <login>` | Fills the formula for this film and prints the title, the labels, the reference files it would upload and the body. It refuses while a slot is missing, or when the formula is not a work order |
| `order … --create` | Needs the film issue first. Uploads the references to the CDN, creates the work order in the film issue's repository, adds its line to the film issue and records it in `project.json → orders` |
| `submit <issue> <file>…` | For a machine that holds the CDN keys. With `--create` it uploads the files to `work/<film>/<issue number>/<file>`, posts the receipt as a comment and sets `status:review`. In Machine the Submit button does the same and needs no keys |
| `advance`, `approve` | These record themselves. When the project has a film issue, each one ticks its stage or its approval on the film issue and adds a comment: `advance: <stage> · <deliverable> · sha <hash> · by <login>` or `approved: <gate> · <version> · by <login>`. If GitHub cannot be reached, the command warns and the ledger is still updated |
| `status <ID>` | Also lists the work orders and the contributors: who did what, and when |

**The labels**

| Label | On | Means |
| --- | --- | --- |
| `dept:video` | both | The work belongs to the Video department |
| `film` | the film issue | This issue is a film's tracker |
| `for:<login>` | a work order | The one person the order is for. Nobody else can start it |
| `P2` | both | The priority both are created with |

Three more labels appear as the work moves, and the machines set them: `holder:<login>` when the
person starts the order, `status:in-progress` while it is being done, and `status:review` once the
receipt is posted. Only the CEO closes an issue; the film issue closes after publish.

The body of a work order is a filled formula, and its references are links, never paths on one
computer. What a formula is, how an order is filled, and one order followed from the command to the
closed issue are on the [Station](/docs/station) page.

## Project folder

Projects live outside every repo, in `~/media/_projects/<ID>/` (override with `PRODUCE_HOME`):

```text
hogwarts-intro-introduction-v001/
  project.json            the ledger
  00-plan/                the locked specs and the plan
  01-brief/ 02-research/ 03-script/ 04-storyboard/
  05-assets/ 06-production/ 07-audio/
  08-render/ (previews, masters, delivery)
  09-quality/ 10-publishing/
```

The ID is `<brand>-<type>-<subject>-v<NNN>`, for example `hogwarts-feature-attendance-v001`. It
names the production line (`hogwarts`), never the public brand. The type comes from the catalogue in
[Video types and names](#video-types-and-names). `produce validate <file>` checks a
`project.json` or a `shot-list.json` against the schemas.

## Lock the line

A **spec** is one stage's decisions written down: what will be made, with which tool, from which
inputs, into which files. A **lock** is a spec recorded in the film's ledger, with who, when and a
hash. The **plan** is all 14 locked specs compiled into one ordered list. A lock freezes a decision
before work. A gate approves a result after it.

```bash
$P lock <ID> --all [--plan <file>] [--set k=v]…     # lock all 14 stages
$P lock <ID> <stage> [--set k=v]… [--spec <file>]   # lock or re-lock one stage
$P unlock <ID> <stage>                              # remove a lock, keep the files
$P plan <ID>                                        # recompile and print the plan
```

`lock` writes files on this Mac only, and repeating it is safe, so it needs no `--create`. Add
`--by <login>` to name who locked, `--json` for a machine answer, and `--no-sync` to leave the film
issue alone. Without `--no-sync`, a film that has an issue gets its body rewritten.

**Where the files go.** Everything is in one folder at the top of the film:

```text
~/media/_projects/hogwarts-intro-introduction-v001/00-plan/
  01-request.spec.json   01-request.spec.md      one pair for each stage, 01 to 14
  …
  14-publish.spec.json   14-publish.spec.md
  plan.json  plan.md                             the plan, compiled from the specs
  plan.input.json                                the plan file that was given with --plan
```

**How a stage's decisions are assembled.** Each stage owns some choices (`stages.json → owns`; the
choices themselves are in `settings.json`). For each choice, the first that exists wins, last to
first:

1. the choice's default, from `settings.json`,
2. the plan's pick, `plan.picks.<choice>`,
3. the plan's entry for the stage, `plan.stages.<stage>.decisions.<choice>`,
4. a `--set choice=value`,
5. the `--spec` file's `decisions`. A spec may carry extra keys; they are kept.

An existing spec is kept unless something overrides it, so `lock --all` run twice changes nothing,
and `lock --all --set voice=source` changes only the audio stage. With `--all`, each `--set` goes to
the stage that owns it. With one stage, a `--set` the stage does not own is an error:

```text
produce: --set look: audio does not own it (owned by visual)
```

The `--plan` file is what the app saves at Accept. Every field is optional:
`{ "picks": {…}, "film": {…}, "stages": { "<stage>": { "decisions": {…}, "tool": "<tool id>", "notes": "…" } }, "cost": ["…"] }`.
The `--spec` file is the `kun-spec` block of a stage discussion:
`{ "stage": "<stage>", "decisions": {…}, "tool": "<tool id>", "notes": "…" }`. Its `stage` must equal
the stage on the command line, and a `tool` that is not in `stages.json → tools` is refused.

**What a lock records.** In `project.json`, `locks.<stage>` holds `{ by, at, sha, source }`. `sha` is
the hash of the spec file. `source` says where the decisions came from: `plan` (from `--all --plan`),
`default` (`--all`, nothing in the plan for that stage), `set` or `spec`. A stage that was already
done when it was locked gets `backfill: true`, and a done stage that is locked again with a changed
spec gets `changed: true`.

**A changed stage holds the line.** While a lock says `changed`, `advance` refuses every stage after
it: `"request" was re-locked after it was done: redo it first`. Redoing that stage
(`produce advance <ID> <stage> --file …`) clears the mark, and the stages after it can go on.
`--force` skips the check.

**A real run.** A throwaway film was created and locked (the film id is written as the documented
one; the home folder is `~`):

```bash

```

```text

```


`unlock` removes the lock and keeps the spec files. After `unlock … visual`, the command printed
`visual — locked 13 of 14`, both `07-visual.spec.*` files were still there, and the plan showed the

**`advance` refuses a heavy stage without a lock.** The heavy stages are visual, audio, edit and
render. After the script is signed off, advancing `visual` with no lock printed:

```text
produce: "visual" is not locked: lock its spec first (produce lock hogwarts-intro-introduction-v001 visual [--set k=v]…, or produce lock hogwarts-intro-introduction-v001 --all), or pass --force
```

The refusal comes after the existing script-gate check. Before the script is signed off, `advance`
still gives the older message about signing the script off.

**The film issue shows the locks.** Each stage line of `produce issue <ID>` ends with
`· locked by <login>`, and a `## Plan` section links `plan.md` and says how many stages are locked
(`locked: 13 of 14` in the run above). A lock made from the app is local and instant; the issue
shows it the next time it is rewritten (an advance, an approval, or `issue --sync`).

**A film that already exists** is locked with one command, `lock <ID> --all`, which takes the
defaults. A stage that was already done is marked `backfill: true`. Nothing is renamed.

## One path rule, and `mirror`

A film's folder and the CDN follow one rule, so a link can be known before anything is uploaded:

| Where | Path | Written by |
| --- | --- | --- |
| A file in the film's folder | `~/media/_projects/<film>/<path>` | the stages |
| The same file on the CDN, as a key | `work/<film>/ref/<path>` | `order --create`, `mirror --create` |
| The same file on the CDN, as a link | `https://cdn.databayt.org/work/<film>/ref/<path>` | |

`url --path` prints the link of any file in the film's folder. It rejects an absolute path and a
path with `..`:

```bash
node ~/.claude/skills/produce/scripts/produce.mjs url hogwarts-intro-introduction-v001 --path 03-script/script.md
```

```text
https://cdn.databayt.org/work/hogwarts-intro-introduction-v001/ref/03-script/script.md
```

```text
produce: --path must be relative to the film folder, with no ".." (got "/etc/passwd")
```

The link is the same one a work order already uses for its references.

`mirror` copies a stage folder to the CDN under that rule. Like every produce command that writes
outside this Mac, it is a **draft** unless `--create` is given. The name is `mirror` because `sync`
already means two other things in kun.

```bash
produce mirror <ID> [--stage <stage>] [--create]
```

Without `--stage`, it takes every stage folder and `00-plan`. Some files are never sent, and the draft
lists each one with its reason:

| Skipped | Why |
| --- | --- |
| `08-render/**` | Masters belong to the video tier; `produce ship` sends them |
| `.ttf`, `.otf`, `.woff`, `.woff2` | Fonts are never rehosted |
| A file over 50 MB | Too large for a mirror |

A draft for the script folder, with a font in it:

```text
DRAFT — nothing uploaded. Add --create to mirror to the CDN.
film: hogwarts-intro-introduction-v001

03-script/ (2 file(s))
  03-script/notes.json
    => https://cdn.databayt.org/work/hogwarts-intro-introduction-v001/ref/03-script/notes.json
  03-script/script.md
    => https://cdn.databayt.org/work/hogwarts-intro-introduction-v001/ref/03-script/script.md

skipped:
  03-script/f.woff2 — fonts are never rehosted
```

For a master and a file over the limit, the draft listed `08-render/masters/master.mp4 — masters
belong to the video tier (ship)` and `05-assets/big.mov — over 50 MB`. With `--create`, each file is
uploaded, then an `index.json` is written in the stage folder and uploaded too:
`{ "film", "stage", "files": [ { "path", "url", "sha", "bytes" } ] }`.

**Three tiers share the CDN.** They never overlap:

| Tier | Key | Holds |
| --- | --- | --- |
| Working files | `work/<film>/ref/<path>` | A film's folder, mirrored. Also the references of a work order |
| Work-order submissions | `work/<film>/<issue number>/<file>` | What a teammate submits for one order |
| The shipped master | `<brand>/video/<type>/<subject>/<variant>/fb-9x16.mp4`, with an archive in `_v/<Vnnn>/` | The approved film. See [CDN keys and the URL grammar](#cdn-keys-and-the-url-grammar) |

The tiers are described on the [CDN](/docs/cdn#work-tier-work) page.

## Markets & versions

One film ships as many **versions**: a market (`sa`, `ae`, `eg`, `sd`) times a language (`ar`, `en`). Markets live in one
file, `content/media/markets.json` — currency, on-screen price, a currency symbol (an SVG for the riyal and the dirham, in
`content/media/currency/`), numerals, languages and the Arabic voice dialect. A version is `<market>-<lang>`: `sa-ar`, `eg-en`.

```bash
$P init --brand hogwarts --identity balqalam --category intro --subject introduction \
  --markets sa,ae,eg,sd
$P set <ID> markets sa,ae,eg,sd      # or add them to an existing project
$P set <ID> slug introduction/owners  # only to change the default <type>/<subject>
```

The film prices follow the pricing decision D-20261117: 24 SAR, 24 AED and 6.40 USD (Egypt, Sudan,
Rwanda), each per student per year. They are read from `content/media/markets.json`, the same file
the station's formulas and the Sales quote use, so a film never states a price the product does not charge.

## Shared vs per-version stages

Stages 01–07 (request, research, brief, script, storyboard, assets, visual) are **shared**: done once, whatever the version
count. Stages audio, edit, render, qa, approval, cdn and publish are **per version**, recorded in
`project.json → variantStages[<variant>][<stage>]`. `status` prints the shared table, then a version × stage grid
(✓ done, · todo, ✗ failed) and each version's predicted URL.

`advance <ID> <stage> --variant <v>` records a per-version stage; on a multi-version project it errors with the list when
`--variant` is missing. `approve --version V001 --variant <v>|--all` pins each version's master sha and refuses any version
whose QA has not passed. A project created without `--markets` keeps the single-line flow, one version per language.

## build and url

```bash
$P build <ID> --variant sa-ar|--all [--dry-run]   # piece.mjs → assemble.mjs, per version
$P url <ID> [--variant sa-ar]                     # predicted URLs, known before the render
$P url <ID> --path <file>                         # the CDN link of one file in the film's folder
```

`build` runs `piece.mjs`, which writes the resolved script `03-script/variants/<v>.json` and the FilmCraft piece
`06-production/editing/<v>.video.json`, then `assemble.mjs --aspect 9:16 --deliver`, and records audio, edit and render for
that version into `08-render/<v>/fb-9x16.mp4`. A version whose inputs hash (resolved script + piece + its market entry) is
unchanged since its last render is skipped, so a price change rebuilds only the affected versions. `--dry-run` writes the
script and piece and stops; a real build needs the script sign-off.

## CDN keys and the URL grammar

```text
https://cdn.databayt.org/<brand-cdn>/video/<type>/<subject>/<variant>/fb-9x16.mp4   stable: always the approved latest
                                                          /<variant>/poster.webp, <lang>.vtt
https://cdn.databayt.org/<brand-cdn>/video/<type>/<subject>/manifest.json          every shipped version, sha, approvedAt
https://cdn.databayt.org/<brand-cdn>/video/<type>/<subject>/_v/V001/<variant>/…    immutable archive per version
```

Example: `https://cdn.databayt.org/hogwarts/video/feature/attendance/sa-ar/fb-9x16.mp4`. The slug is `<type>/<subject>`
(one slash, lowercase letters, digits and hyphens). It is set by `init` from the type and the subject, or by `init --slug`,
so the URL is known before anything renders. `ship <ID> --variant <v>|--all` uploads the `_v/` archive first,
then the stable keys, then the merged manifest, and refuses if another film already owns the brand and slug. `--dry-run`
prints the key list only. Projects without markets keep the legacy keys:

```text
<brand>/video/<ID>/{master.mp4, fb-16x9.mp4, fb-9x16.mp4, fb-1x1.mp4, <lang>.vtt, poster.webp, manifest.json}
video/index.json        approved videos only
```

`<ns>/<lang>/<flow>/video.mp4` tutorial keys are a different tier. Run `ship --dry-run` first.
See [media](/docs/media) and [cdn](/docs/cdn).

## Identity

**brand** is the production line and the ledger code. **identity** is the brand-kit face that
appears on film: name, wordmark, colors. It defaults to the brand. Set it at creation with
`--identity balqalam`, or change an existing project with `produce set <ID> identity balqalam`.
Brand tooling, captions and the end card read `brand-kit[identity]`, so a Balqalam piece never
carries the Hogwarts wordmark, and a Hogwarts piece never says بالقلم. The Hogwarts intro film
is made for school owners under the Balqalam identity.

## From a source video

A film can start from a video that already exists. Its words become the script. Its sound becomes the voiceover. The picture is rebuilt over that timing from 3D scenes, real app captures and generated images.

```bash
P=~/.claude/skills/produce/scripts/produce.mjs
node $P init --brand hogwarts --identity balqalam --category introduction --subject owners --lang ar --markets sd
node $P from-reference <ID> ~/Downloads/balqalam-promo-v2.mp4 --voiceover
```

`from-reference` does four things:

1. Copies the video to `02-research/reference/video.mp4` and cuts a contact sheet.
2. Transcribes it with `mlx_whisper` into `transcript.srt`.
3. Seeds `03-script/script.md` from the transcript. The research stage is marked `seeded`.
4. With `--voiceover`, extracts the audio as a 48 kHz mono wav to `07-audio/voiceover/<variant>.wav`.

The wav is the timing master. Its record sits in `project.json → voice.<variant>`: the source video, the file, the sample rate and the length in seconds. A project with one variant needs no more. A project with several variants needs `--variant <v>` for one, or `--all` for the same sound on every variant. Nothing is copied before the variant is known.

A file with no audio is refused. A failed transcription keeps the copy and the wav.

Two commands feed Machine. Both print JSON.

| Command | Prints |
| --- | --- |
| `produce list --json [--repo <line>]` | Every project, newest first: id, title, brand, identity, category, version, status, next stage, focus, variants, markets, langs, dir |
| `produce status <ID> --json` | The 14 stages (`stage_list`), the variant grid (`variants`), the gates, `next`, the predicted `urls`, `paths` and `files` for the script, `04-storyboard/shot-list.json` and `05-assets/asset-manifest.json`, `voice`, and the locks and the plan (below) |

`status --json` gives the app every path and link it needs, so the app and the formulas never build
one themselves. These fields are new:

| Field | Where | What it holds |
| --- | --- | --- |
| `dir` | each `stage_list[]` entry | The stage's folder, for example `06-production` |
| `spec` | each `stage_list[]` entry | The absolute path of the stage's spec file, or `null` before it is written |
| `spec_url` | each `stage_list[]` entry | The spec's CDN link |
| `file_url` | each `stage_list[]` entry | The deliverable's CDN link, or `null` for a stage with no file |
| `locked` | each `stage_list[]` entry | `true` when the stage has a lock |
| `locks` | top level | The ledger's locks: for each locked stage `{ by, at, sha, source }` |
| `plan` | top level | `{ json, md, url, locked_all }`, or `null` before the first lock |

The video department works in English. Questions, plans and replies are English. A film's version language (`language`, `dialect`) applies only to the film's own words: the script, the captions and the voiceover.

## From Machine

In Machine, the home of the **Video** department shows at most three options. They are
chosen by the station's board from the formulas in `departments/video/formulas/` and from this
ledger's state: an open project, the stage it has reached, an approval that waits. With a Hogwarts
film in production, the options on 2026-11-22 were:

| Option | What a tap does |
| --- | --- |
| Continue production | Fills the prompt for the stage the open film has reached |
| New film | Fills the prompt that plans a new film. Nothing is created until the plan is accepted |
| Video script | Fills the prompt for a video script on its own |

A tap fills the prompt with a script; no model runs. The [Station](/docs/station) page explains the
board and the formulas, and the [Video pipeline](/docs/pipeline) page follows a film from the home
screen step by step.

### Get the computer ready (in the app)

Everything a video machine needs is set up from the app, not the Terminal:

| Where | What |
| --- | --- |
| **Apps** | Blender, FilmCraft, whisper-cli, OBS, ffmpeg and, when a film needs them, ComfyUI and ArtCraft. **+** installs, **…** uninstalls |
| **Setup → Accounts / Identity** | GitHub sign-in and SSH key, Claude sign-in, Figma for the look |
| **Setup → the doctor** | The video department's minimum: the video pack (produce, edit, record, shoot, blender, higgs, the video and media-qa agents), the engine's hooks and rules, Blender, FilmCraft, whisper-cli and a real Whisper model |

The doctor shows one of three levels. **Green**: everything passes. **Orange**: the minimum is there
and some extras are missing (for example the Whisper model); you can chat and contribute, and the
app names what is missing. **Red**: the minimum shared intelligence is missing; you can still chat,
but you cannot take or submit work until it is fixed. The doctor runs on its own the first time the
app opens and after every update. See [Machine](/docs/machine).

### Make a film from the app

1. **Home → Department: Video → Repo: Hogwarts.**
2. **Say what you want**, in English, for example "intro film for hogwarts". Attach a source video from **+ → Videos** if the film starts from one. A chip
   offers the standard formula (`⇥ Tab · Intro film · Balqalam · 9:16`); **Tab** fills it. Tapping
   **New film** on the board does the same.
3. **Send.** The chat starts and the plan run asks its own questions in a wizard (Enter, ↑/↓, Tab,
   Esc; "Type something" or "Chat about this" if no option fits). Your answers go back to the same
   session, it may ask again, then it writes the plan. Nothing is created until you **Accept**. Accept
   turns the plan into the next phase's prompt, locks the 14 stages, opens the film issue and a work
   order for each piece handed to another person. The model is chosen for you (Settings → Model).
4. **The four gates are yours.** Script, look (animatic), version and publish each stop for your
   approval; the app never approves. Between gates, **Continue production** on the board fills the
   next stage.
5. **Heavy steps** (a Blender render, transcription, the encode) run on this computer, or as a
   [shared job](/docs/machine#share-when-idle) on a teammate's idle machine.
6. Files land under `~/media/<line>/<film>/`, and approved masters go to the CDN as described above.
