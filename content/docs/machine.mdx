# Machine

> The desktop app for people who do not live in a terminal. It wraps the same Claude Code the engine uses, shows the skills and agents of **their department**, and keeps everything on their own computer.

Machine is a small Rust + Tauri 2 app that lives in its own repo, [databayt/machine](https://github.com/databayt/machine) (moved out of kun on 2026-11-17). The window shows a bundled static export of the UI (local-only IPC, no remote origin); every feature's Rust lives beside its UI in `src/components/<feature>/rust.rs`. It talks to kun.databayt.org (`/api/machine/*`, served by this repo) and GitHub. Development instructions (build, test, CI) are in that repo's README. It never proxies a model: it starts the unmodified `claude` binary, signed in with the teammate's own account.

## Install on Windows 11

Needs Windows 11, an internet connection and GitHub access to `databayt/kun`. Open **PowerShell** and run (one line):

```powershell
irm https://raw.githubusercontent.com/databayt/kun/main/.claude/scripts/setup.ps1 -OutFile $env:TEMP\kun-setup.ps1; powershell -ExecutionPolicy Bypass -File $env:TEMP\kun-setup.ps1 -Machine moed
```

If the repo is private, or the installer is a file you were handed, clone first (Git opens a browser sign-in) and run from the clone:

```powershell
cd $env:USERPROFILE\kun; powershell -ExecutionPolicy Bypass -File .\.claude\scripts\setup.ps1 -Machine moed -MsiPath $env:USERPROFILE\Downloads\Kun.msi
```

`-Machine <login>` is the **only** thing the script does for a machine login. It is safe to re-run: every step checks first.

| Step | What happens |
| --- | --- |
| Windows 11 | Checks the build; warns on anything older |
| Git | Installs it with `winget` if missing |
| WebView2 | Checked; Windows 11 ships it, and the installer downloads it if not |
| Claude Code | Installed with the official installer (`irm https://claude.ai/install.ps1 \| iex`) |
| kun | Cloned to `%USERPROFILE%\kun` (machine reads `machines\` and `departments\` from it) |
| Settings | Writes `%USERPROFILE%\.kun\machine\settings.json` from `machines\<login>.json` |
| Machine | Installs the `.msi` you pass with `-MsiPath` or `-MsiUrl`, else the latest release of `databayt/machine` |

It does **not** run the engine install: no hooks, no rules, no full skill set. The app's catalog installs the items of the person's profile.

With no `-MsiPath` or `-MsiUrl`, the script downloads the `.msi` of the [latest release of databayt/machine](https://github.com/databayt/machine/releases/latest); a build artifact of that repo's CI also works (pass it with `-MsiPath`). The installer is unsigned. Because it is unsigned, Windows SmartScreen stops it once on first launch: press **More info**, then **Run anyway**.

## First run

1. In PowerShell run `claude` once and sign in with **your own** Claude account. Nobody signs in for you.
2. Open **Kun** from the Start menu. The app picks up your name, department and agent from `settings.json`.
3. The app opens on **Install** until the computer is ready. Press **Install everything**, sign in where it asks, then open **.claude**, then **departments**, and install your department's pack. After that, ask in Arabic or English.
4. Voice (optional): press the microphone, and the app downloads a small speech model once (about 142 MB). It runs on the CPU and nothing leaves the computer. A larger, slower, more accurate model (`small`, about 465 MB) can be chosen instead. Spoken replies use the Windows voices.

## The sidebar

The sidebar is the whole navigation. There is no title, toolbar or tab row in the work area: a screen shows content only. Click a link and its sub-links open under it; click one of those and the screen swaps to it. The lines under the open link are your path, so the sidebar is also the way back: click any line above to go up a level. On a narrow window the same four links are in the menu.

| Link | Open it when | What is under it |
| --- | --- | --- |
| **Sessions** | You want a chat you had before | Every past chat on this computer: reopen, rename, delete |
| **Install** | The computer is new, something stopped working, or you want something removed | The seven stages of a ready computer, each with its count (`9/11`), then each stage's steps |
| **.claude** | You want to see, add, remove or switch off what the agent can do | The folders of `~/.claude`: `skills`, `agents`, `rules`, `hooks`, `departments`, `mcp` |
| **Settings** | You are changing how the app or the engine behaves | General, Config, Health, Engine |
| Docs | You want to read how something works | Opens these pages in the browser |
| Mathematics | You want the curriculum walk-through | Starts a chat about it |

The number beside **Install** (`· 82%`) is how ready the computer is; it disappears at 100%.

**Settings, link by link**

- **General**: language, who you are and your department. (The default agent is under **Install**, then **Agents**, then **Default agent**; every repo is under **Install**, then **Repos**, then **All repositories**.)
- **Config**: the notifications line, your personal `settings.json` keys and the team secrets file. Every change is backed up first, and a failed health check puts the old content back.
- **Health**: the engine's health check and app updates.
- **Engine**: the engine's version and its own update. Hidden on machines whose profile does not manage the engine.

## The home screen

The home is where a request starts. It shows a greeting, the input box, and one line under the box: **Department ▾**, **Repo ▾** and the health light. Under that line there are at most **three options**.

**The three options.** They are not a fixed list. They come from the station's board: a script reads your department's *formulas* (prompts written in advance, one file each) and the state of the work, and returns one option for each of three roles.

| Role | What it offers |
| --- | --- |
| **Waiting** | Something that waits for you: one of a film's four approvals (script, look, version, publish), or a work order made for you |
| **Next** | The next step of work that is already open |
| **Start** | Something new |

When a role has nothing to offer, the next best option takes its place, so you may see two options of one kind. How to use them:

- **Tap an option** and the full prompt fills the box at once. No model runs, and nothing is sent until you press Enter. You can edit the prompt first.
- **The ✕** at the end of a row takes that option off the list for this visit.
- **If the board cannot answer**, the department's own short list from its pack shows instead, so the home is never empty for that reason.

**Typing your own.** Write in Arabic or English and press the sparkle button beside the microphone. The app first looks for a formula that fits your words and fills it, with no model. Two kinds of sentence are understood as well as plain requests:

- **A hand-over.** "Give the classroom scene to sedon" fills the work order for that piece, with the person and the piece already written in. Sending it asks the agent to create that issue for the person; it does not start the work on your machine.
- **Another department.** "Sales quote a school for 48 students", typed while you are in Video, moves the Department menu to Sales without asking and fills Sales' quote.

Only when no formula fits does a short Claude run rewrite your words into a full prompt.

**Accept, under a plan.** A request that runs "plan first" comes back as a plan, and nothing has been changed yet. A typed reply answers or changes the plan, and still changes nothing. One button under the plan, **Accept** (اعتمد الخطة), turns it into work. What that means depends on what was planned. Under a film plan, the department's lead puts the film on GitHub: it creates the film issue, and a work order for each piece the plan gives to another person, and replies with the links. Under a plan for one work order, it creates that work order. Under any other plan it carries out the first step and stops at the next approval.

**The Repo menu.** The list is not built into the app. It is the repos your department's pack and your profile name, limited to the ones kun's registry (`.claude/memory/repositories.json`) marks active, with Hogwarts first. A repo that has a word of its own in the registry shows that word: the databayt.org site repo is called `marketing` on GitHub and shows as `landing`.

The whole design is on the [Station](/docs/station) page, and the [Video pipeline](/docs/pipeline) page walks through it step by step for the Video department.

## The production strip

In the Video department, once a film exists, a one-line strip sits above the chat input: the film's name, one dot per stage, the stage it has reached and its gates. With several films, a select picks one.

Click it and it grows upward over the transcript. The input does not move. Three tabs:

| Tab | Shows |
| --- | --- |
| **Stages** | The 14 stages with their gates |
| **Scenes** | The shot list against the asset manifest: a thumbnail per capture, an icon for 3D, image, capture or video, and a mark on what is missing |
| **Brand** | The logo, the fonts drawn in their own face, the colour swatches and the voice. Read once and kept |

There are no action buttons. Clicking a stage or a scene fills the box with the matching `video.stage.*` or `video.order.*` formula, the same way a tap on the home does. The chat stays the only place where anything runs. The strip reads `produce.mjs list --json` and `status <ID> --json`, with no shell. A video picked from **+ → Videos** fills the `source` slot of the film plan. See [Video pipeline](/docs/pipeline).

## Install and uninstall

Install is the wizard. It follows the same catalog the one-liner uses (`.claude/machine/readiness.json`), so the app and the terminal never disagree about what "ready" means.

| Stage | What it covers |
| --- | --- |
| Identity | GitHub CLI, GitHub sign-in, membership of the databayt organization, SSH key, git name and email |
| Accounts | Claude sign-in, Slack, the company mailbox, team secrets, CRM keys, Figma for tech, image and marketing, and for tech Cloudflare, Vercel, AWS and Neon |
| Foundation | Homebrew, git, Node 24, pnpm, jq, uv, ffmpeg, tesseract, tmux, Chrome, Colima |
| Repos | The repos folder, the kun, hogwarts and codebase clones, each product's `.env` |
| Agents | Claude Code and Desktop, Antigravity, opencode, Codex, Hermes |
| Engine | The engine's config in `~/.claude`, its MCP servers, the daily heartbeat, the devices lane |
| Tools | Your department's apps: WebStorm and VS Code for tech; Blender, FilmCraft, OBS and ComfyUI for video |

How to use it:

1. Open **Install**. The first screen shows how ready the computer is and one button, **Install everything**. It runs every step that needs no person.
2. Steps that need you are marked. Each has one button that takes you to the right place: **Sign in** opens Terminal with the command, **Open** opens the page (for example the organization invite), **Ask Abdout** sends him the request.
3. Open a stage to see its steps, or one step to see the exact command it runs and what it waits for.
4. **Heal with agent** hands whatever is still failing to Claude, in the kun folder, with the `provision` skill.

**Uninstall** is on every step the wizard installed. Before it removes anything the app shows what still depends on the step, and it refuses while something installed needs it.

- Apps and command-line tools are removed with the same tool that installed them.
- Repos and `.env` files go to the **Trash**, not deleted. A repo with uncommitted, stashed or unpushed work is refused.
- Sign-ins are signed out in Terminal.
- **Homebrew, Node, the kun repo and Claude Code are keystones**: the app itself stands on them. The app never removes them by itself. It opens Terminal with the command and tells you that Machine cannot install anything afterwards; the [one-liner](/docs/onboarding#the-one-liner) brings it all back.
- Steps with nothing on the computer to remove (organization membership, Slack, CRM keys) have no Uninstall.

What you remove stays removed. The step shows as **removed by you**, it no longer counts against the percentage, and the daily heartbeat does not put it back. Press **Install** on it to bring it back.

## The `.claude` control room

**.claude** shows the agent's config folder the way Finder shows a folder: folders and files, nothing else.

| Folder | What is in it | What you can do |
| --- | --- | --- |
| `skills` | What the agent knows how to do (`draft`, `deploy`, `funnel`, …) | Install, uninstall, switch on or off |
| `agents` | The specialists it can hand work to | Install, uninstall, switch on or off |
| `rules` | Standing instructions it always follows | Install, uninstall, switch on or off |
| `hooks` | Scripts that run on events | Install, uninstall |
| `departments` | A department's pack: its skills and agents in one item | Install the pack, or open it and pick items |
| `mcp` | The outside services the agent can reach | Switch a server on or off |

The first screen also shows three files, `CLAUDE.md`, `settings.json` and `.env`; opening one takes you to **Config** under **Settings**, where they are edited. Each folder ends with one line, for example `86 items · 61 on`.

How to read a folder:

- A normal icon is **installed** and on.
- A dimmed icon with a download mark is **available** from kun but not on this computer. Open it and press **Install**.
- A greyed icon is **switched off**: the file is kept aside, and the agent no longer sees it. The switch under the icon brings it back exactly as it was.
- A blue dot means kun has a newer version: open it and press **Update**.
- An icon with a person mark is **yours**: something you made. The app can switch it off, and it never deletes it.

The difference between the two verbs: **switch off** keeps your copy and is undone with one click; **uninstall** removes kun's files. Both survive the daily engine refresh, which otherwise copies every engine item back.

Hooks have no switch on purpose. A hook is wired from `settings.json`, and a missing file would raise an error on every event; install or uninstall it instead.

## What Moed's machine can and cannot do

Profile: `machines/moed.json` — departments **sales**, **marketing**, **video**; agent **Claude**.

**Can**

- Sales: proposals, pricing, scrape and funnel once the Twenty key is set.
- Marketing: draft, calendar, social, carousel, measure and approve. Publishing stays behind kun's approve queue.
- Read the kun, hogwarts and mkan repos; write only in his own workspace.
- Talk to the agent in Arabic or English, by text or voice, and hear replies.

**Cannot**

- Change code in the repos (read-only) or touch the engine (hidden for this login).
- Use the video lanes (edit, shoot, record, higgs) until each is ported: they still have macOS-only steps and are marked Mac-only in his menu.
- Publish anything on a brand page without a human approval.
- Run the engine's hooks or its Mac-only scripts.

## Free models

Settings has a **Model** page with four routes: **Claude** (the default, on your own sign-in), **NVIDIA** (Nemotron 550B through Free Claude Code, a free key), **OpenRouter** (free models; 50 requests a day, or 1,000 after a $10 top-up) and **OmniRoute** (stacks the free tiers). Each is opt-in, per person.

- Keys live in the keychain; the app only shows "set" or "not set". Get them from build.nvidia.com/settings/api-keys and openrouter.ai/keys.
- The app starts the local proxy itself (`fcc-server` on `127.0.0.1:8082`, or `omniroute serve --headless` on `:20128`) and stops only a proxy it started. The installs are readiness steps `fcc.cli` and `omniroute.cli` on the Apps page.
- A free provider can read what a run sends. **Keep client code on Claude.** The company pays $0; any OpenRouter credit is your own.
- A route that is chosen but not ready fails with one line naming the missing step. It never falls back to Claude silently.

## Machines

The **Machines** page lists every machine on the network: name, OS, department, an online dot (seen in the last 15 minutes) and one line of resources, for example "M4 Pro · 48 GB · 20-core GPU · 120 GB free · on power". Open one for every row: CPU, RAM, GPU, free disk, Google Drive (read locally from Drive for desktop, no Google sign-in), internet, power, last seen, current task, readiness percent and the doctor verdict.

Each heartbeat carries these as optional fields, so an older app or a failed read still reports. kun keeps the last values on the machine's row and serves them in `GET /api/machine/team`.

## Pool

Heavy jobs can run on a teammate's idle machine. It is opt-in on both ends.

- **Donor.** Turn on **Share when idle** on your machine card and pick the kinds you accept. A job is claimed only when you are on mains power, idle for at least 10 minutes (configurable), have the RAM and disk the job needs and the tool installed. If you come back, the run stops and the job goes back to the queue.
- **Kinds are fixed templates:** `transcribe` (whisper to `.srt` or `.txt`), `render` (Blender, frame range and engine) and `encode` (ffmpeg presets `h264-web`, `hevc`, `proxy`). Parameters are validated on both ends and never reach a shell. **Claude runs are not a pool kind.**
- **Requester.** On the Machines page choose **Send a job**, pick a kind and files, optionally target one machine, and send. The job starts as `uploading`; when every input is uploaded the app calls `POST /pool/ready` and it becomes `queued`, which is the only state a donor can claim (an `uploading` job older than 24 hours is cancelled). Jobs show status and progress, with **Download** when done, and when a donor finishes you get a note in your messages ("Pool job … is done on … machine").
- **Doctor.** A donor whose doctor level is red (a core step missing), or whose non-green verdict is older than 48 hours, is refused with `doctor`, like a task claim; orange (only extras missing) is allowed with a warning (see [Onboarding](/docs/onboarding#doctor)).
- **Files** go through presigned links under `pool/<jobId>/` (2 GB each; downloads expire in 10 minutes). The donor deletes its local copy when the job ends, and the bucket expires `pool/` after 7 days.
- **Reliability.** Claiming is an atomic compare-and-swap, a job is claimed at most twice, and a running job silent for 15 minutes returns to the queue.

API (bearer token): `POST /api/machine/pool` (create), `GET /api/machine/pool` (mine + queue), `POST /pool/claim`, `/pool/progress`, `/pool/ready` (requester: inputs uploaded), `/pool/done` (returns output upload links; up to 50 files, or one archive), `/pool/finish` (marks done and notifies the requester), `/pool/cancel`. The shapes are in `src/lib/machine/contract.ts`.

## Tasks and the gate

Work reaches the app as GitHub issues. The captain and weekly skills draft them; nothing is created until Abdout says "send". Each task carries a `dept:<department>` label, the sprint as its milestone (`Sprint <yyyy>-W<ww>`), a `P0` to `P3` priority and a hidden kun block naming the repos and catalog items it needs and the tasks it waits for (`after`).

A **work order** is a task made for one person: one request, one deliverable. It carries a `for:<login>` label, and its kun block also names the film it belongs to and the formula it was written from. A film's work orders are made with `produce order`, by the department's lead when a film plan is accepted or by hand later ([Station](/docs/station) shows a full example).

A work order made for you shows in two places. On the home screen it takes the Waiting place of its department's board, as the option "Start my work order": the `for:` label counts exactly like an issue assigned to you on GitHub. And it is in the queue below, whatever its department.

What a person sees:

- **The queue.** First come your department's tasks that you hold or that nobody holds, in queue order: priority, then sprint, then age. Then come the work orders made for you in other departments, so an order reaches you even when its department is not yours. Tasks that other people hold come last. The menu shows six at most.
- **Readiness** on the top task: the repos it needs are local and fresh, its catalog items are installed, your profile allows them, every task it waits for is closed, and nobody else holds it. Anything missing is listed with a one-tap fix (clone the repo, install the items).
- **The doctor.** The doctor has three levels: red (core steps missing, contributing blocked), orange (only extras missing, contribute with a warning) and green. Start is refused with `doctor` only while the level is red or a non-green verdict is older than 48 hours; chatting with the shared intelligence, the org and every repo is never blocked. It runs on its own at first launch and after updates, and the Setup page shows what is left while **Fix automatically** runs the safe fixes ([Onboarding → Doctor](/docs/onboarding#doctor)). The team list (`GET /api/machine/team`) carries each machine's `readinessPercent` and `gate`.
- **Start**, once ready. It claims the task (it shows as in progress, with a comment saying which machine) and opens a chat seeded with the issue, its kun block and the repos. A work order can be started only by the person it was made for.
- **One task at a time.** Start is refused while you hold another in-progress task, unless the CEO has granted `wip:2`. Release hands a task back.
- **Done** moves it to review with a summary comment. It is not finished yet.
- **Submit** hands in the files of a task you hold. In the task's chat, write one line about the work in the box, press **Submit** (سلّم العمل) and choose the files. A line in the box that starts with `next:` is kept apart as the line for the next person.
  - **What it uploads.** The files you chose, at most 20 at a time, from your home folder or an external drive and never from a hidden folder. Each file goes straight from your computer to the CDN, to `work/<film>/<issue number>/<file>`, through a short-lived link that kun hands out. No cloud key is ever on your computer.
  - **The progress line.** One line under the box names the file being sent and its percentage, then says the receipt is being sent, then "Submitted. It is waiting for review." If kun refuses, the line shows kun's own reason.
  - **The receipt.** When every file is up, the app posts one comment on the issue: your summary, the link to each file, a sha256 hash of each file and the line for the next person. The task moves to review. Nothing is posted unless every file arrived.
- **The CEO closes it.** Only a closed issue counts as done, so nothing is skipped silently, and tasks waiting on it become ready.

Holder and status labels are managed by the machines, never set by hand.

## Troubleshooting

| Symptom | Fix |
| --- | --- |
| "running scripts is disabled" | Run it through `powershell -ExecutionPolicy Bypass -File ...` as shown above |
| Clone fails | Sign in to GitHub in the browser prompt Git opens, then re-run |
| `claude` not found after install | Open a new PowerShell window |
| Voice is slow | Keep the default `base` model; do not switch to `small` on a laptop without a GPU |
