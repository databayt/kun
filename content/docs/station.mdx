## What it is

The station is the part of Kun that turns a choice, or a few typed words, into a full request and
sends it to the right place. It works like a central train station. You hold a ticket, a board shows
the trains that leave now, and every train already knows where it is going. Nothing here needs a
model: one script, `.claude/scripts/station.mjs`, does the choosing and the filling, and it costs
zero tokens.

| Station word | In Kun |
| --- | --- |
| Ticket | Who is asking, the department, the repo, and where the work stands: the open film, its stage, an approval that waits |
| Train | A **formula**: a prompt written in advance, with its destination in its header |
| Destination | The route the formula runs on, the gate it stops at, what comes back, and whether it is recorded as an issue |
| Departure board | The three options on the home screen |
| Switch | The code that maps typed text to one formula (`match`). No model |
| Conductor | The code that fills a formula's blanks (`fill`). A model runs only for typed text that fits no formula |
| Signals | The facts the board scores with: waiting, continue, sprint, drive, due and habit |

The [Video pipeline](/docs/pipeline) page shows the same thing from the user's side, step by step.

## The two kinds of word

There are two kinds of word: a **department word** (`video`, `sales`) and a **repo word**
(`hogwarts`, `mkan`). Each word is four things at once: the keyword you say, the slash command, the
agent, and the entry in the app's menu.

| | Department word (`video`) | Repo word (`hogwarts`) |
| --- | --- | --- |
| Where it is defined | `departments/video/pack.json` | `.claude/memory/repositories.json` |
| Keyword | `video`, `الفيديو` | `hogwarts` |
| Slash command | `/video`, the department's door: its board, its formulas, its lead | `/hogwarts`, the place's door: its rules, blocks and open issues |
| Agent | `video`, the department's lead | `hogwarts`, the product reference |
| Menu entry | Department ▾ | Repo ▾ |
| On an issue | the label `dept:video` | the repository the issue is in |

**How to say them.** Say the department first, then the repo, then the request:
`video hogwarts intro film`. In the app the same ticket is Video ▾, Hogwarts ▾ and a tap on an option.

- A department word counts when it comes first in the prompt (`sales: quote a school`,
  `/marketing this week's calendar`), or among the first three words when every word before it is a
  repo or a department (`hogwarts video intro film`).
- Anywhere else it is an ordinary word. "Add support for dark mode" is not the support department.
- The explicit forms work anywhere: `<word> department`, `<word> dept`, `<word> team`, `<word> desk`,
  `department of <word>`, `dept:<word>`, and in Arabic `قسم <name>` or `فريق <name>`.

**Marketing and landing.** `marketing` alone is the department. The databayt.org site lives in a
repo whose GitHub name is also `marketing`, so that repo has its own word, `landing`. Say it first
(`landing fix the hero`), or say `landing repo`, `landing site` or `in landing`.

A repo word gets all four forms once a department's pack lists the repo. Today those are `kun`,
`hogwarts`, `mkan`, `codebase` and `catalog`. Any other repo is a keyword only. One script,
`.claude/scripts/compile-words.mjs`, writes the door skills and the reference agents from the two
sources, so nobody keeps them by hand. The full list of words is on the [Places](/docs/places) page.

## Formulas

A **formula** is a prompt written in advance for one kind of work. It has blanks, called **slots**,
that are filled at the moment it is used. Each formula is one file:
`departments/<department>/formulas/<id>.md`. Video has 37 formulas and Sales has 7.

A formula file has two parts. The first is a header, written as JSON between two `---` lines. The
second is the prompt, under five fixed headings (Task, Context, References, Constraints,
Deliverable), with each slot written as `{{name}}`.

**The header fields**

| Field | What it is | Example |
| --- | --- | --- |
| `id` | The formula's name. It starts with the department and matches the file name | `video.film.plan` |
| `label` | The option's name in English and Arabic | `Intro film` · `فيلم تعريفي` |
| `icon` | The icon shown beside the option | `Film` |
| `when` | When it applies: a sentence for the reader, plus conditions the board checks | `{"project": "open", "gate": "script"}` in `video.gate.script` |
| `route` | The route it runs on (see [Routes and lanes](#routes-and-lanes)) | `plan` |
| `gate` | The gate it stops at, or `null` | `look` in `video.stage.visual` |
| `slots` | The blanks, and where each value comes from | see the next table |
| `drive` | How close the work is to revenue, from 0 to 1. The board scores with it | `1` |
| `weight` | The points the work is worth in the record | `5` in `video.order.blender` |
| `role` | Its place on the board: `waiting`, `next` or `start` | `start` |
| `board` | Whether it may appear on the board | `true` |
| `record` | What accepting it puts on GitHub. `none`: nothing. `issue`: a work order, one issue for one person. `film`: the film issue and its first work orders | `film` in `video.film.plan`, `issue` in `video.order.blender` |
| `triggers` | English and Arabic phrases the switch listens for | `intro film`, `فيديو تعريفي` |

Some formulas carry a few more fields:

| Field | What it does | Used by |
| --- | --- | --- |
| `redirects` | Sends the request to another formula. It is one entry or a list; the first entry whose `if` holds wins. `open_project`: a film is open. `all_locked`: the open film has all 14 stages locked (see [Stages, specs and locks](#stages-specs-and-locks)) | `video.film.continue` has two: `all_locked` goes to `video.film.run`, `open_project` goes to the formula of the film's current stage (`video.stage.{stage}`) |
| `needs` | `["tools"]` hides the formula while the health light is red | `video.film.continue`, `video.reel.footage`, `video.versions.fanout` |
| `due` | The weekdays on which the formula is due | `sales.followup.today` |
| `health_boost`, `health_only` | Bring the formula forward only when the tools are not healthy | `video.tools.check` |
| `submit` | `comment` when a work order's result is a reply on the issue, not a file | `sales.order.call` |

**Where a slot's value comes from**

| Source | The value is | Example |
| --- | --- | --- |
| `context` | A fact of the moment: the repo, your login, today's date, the open film's id or stage | `repo`, `project` |
| `choice` | One of a short list, with a default (the default can differ by repo) | `audience`, `market` |
| `json` | Read from a JSON file in kun | `price` from `content/media/markets.json` |
| `argv` | The output of a read-only command: `node` and a script inside kun or `~/.claude`, never a shell | a film's predicted video link |
| `map` | Looked up from another slot's value | `language` from `lang` |
| `mul` | Numbers multiplied together | the total of a quote: price times students |
| `slug` | Another slot's value made safe for a file name | `scene_slug` |
| `value` | A fixed text | the brand kit's link |
| `ref` | A file in the film's folder, turned into a link | `script_url` |
| `ask` | Nothing: the person must give it | `scene`, `to` |

**Formula or slot?** One rule separates them. A choice that changes the *work* (the stages, the
tools, the gate, what comes back) is a new formula. A choice that only changes a *value* is a slot.
The old Video pack held a tree of 32 ready-made prompts. Their text was the same apart from three
values, so they were really one formula with three slots, and that is what replaced them.

**The three layers.** A finished prompt is built from three layers, each kept in one place:

1. **The frame.** The five headings and what each must hold. It is `pack.json → formula.en`, and
   every formula of the department must use those headings in that order.
2. **The department's constraints.** The rules that hold for every piece of the department's work.
   They are `pack.json → constraints`, and `fill` adds them to the Constraints section of every
   prompt. Video has three: claims only from real captures, no real student or parent data, and stop
   at every human gate.
3. **The formula.** The text of this one kind of work, with its slots.

**One choice can set several values.** In `video.film.plan` the slot `market` is one choice. It sets
the market's name, the price and the currency, all read from `content/media/markets.json`, and,
together with the language, the voice's dialect. Choosing `sd` gives Sudan, 6.4 USD and the `msa`
dialect in Arabic. Choosing `sa` gives Saudi Arabia, 24 SAR and the `saudi` dialect. The price is
per student per year. The language itself is a separate slot, `lang`.

## The board

The board is the list of three options on the home screen. It has three fixed **roles**, always in
this order:

| Role | What it offers |
| --- | --- |
| **Waiting** | Something that waits for you: one of an open film's four approvals (script, look, version, publish), or a work order made for you |
| **Next** | The next step of work that is already open |
| **Start** | Something new |

The board scores every formula that has `board: true`, then takes the best one for each role. When
no formula qualifies for a role, the board fills the empty place with the next best option of any
role. That is why, today, neither department shows a Waiting row.

**What a person sees.** Three plain rows, each with an icon and a name. There is no label for the
role, the score or the route. Hovering over a row shows a ✕ at its end; pressing it takes that
option off the list for this visit and counts against it next time.

**The signals.** A **signal** is one fact about the moment. Each has a weight, kept in
`.claude/engine.json → board.weights`. A formula's score is the sum of weight times signal.

| Signal | Weight | It is on when |
| --- | --- | --- |
| `waiting` | 5 | A gate (script, look, version or publish) waits in an open film, or an open issue with the department's label is yours: it is assigned to you on GitHub, or it carries the label `for:<login>` with your login |
| `continue` | 3 | There is an open project in the department and repo |
| `sprint` | 3 | An open issue in the current sprint carries the department's label and matches the formula |
| `drive` | 2 | Always. Its size is the formula's own `drive`, from 0 to 1 |
| `due` | 2 | The formula's `due` rule names today's weekday |
| `habit` | 1 | You picked this option recently. Picks add and dismissals subtract, over the last 14 days |

Three more things change the board:

- **The health light.** When it is red, every formula that needs the tools is left out and Tools
  check takes the Start place. When it is orange, Tools check is offered. When it is green, Tools
  check appears only if nothing else is left.
- **Your profile.** A formula listed under `hidden` in `machines/<login>.json` is never shown. A
  department that is not in your profile has an empty board, and the app shows the pack's own short
  list (`quickActions`) instead.
- **A film already open.** `video.film.plan` is named "Intro film". While a film is open it is shown
  as "New film", so it does not look like a second way to continue.

**What the board shows today.** These are the two real commands and what they returned on
2026-11-22, a Sunday.

```bash
node .claude/scripts/station.mjs board --dept video --repo hogwarts --login abdout --json
node .claude/scripts/station.mjs board --dept sales --login abdout --json
```

| Role | Option | Formula | Score | Why |
| --- | --- | --- | --- | --- |
| Next | Continue production | `video.film.continue` | 4.8 | `continue: open project hogwarts-intro-introduction-v001` · `drive 0.9` |
| Start | New film | `video.film.plan` | 2 | `drive 1` |
| Start | Video script | `video.script.only` | 1 | `drive 0.5` |

Sales:

| Role | Option | Formula | Score | Why |
| --- | --- | --- | --- | --- |
| Next | Who to follow up | `sales.followup.today` | 4 | `drive 1` · `due today` |
| Next | Log a reply | `sales.reply.log` | 1.8 | `drive 0.9` |

The scores can be checked by hand. Continue production is 3 for `continue` plus 2 times 0.9 for
`drive`, which is 4.8. Who to follow up is 2 times 1 for `drive` plus 2 for `due`, which is 4.

## The settings menu

The home screen has a **gear** in the chat box. It opens a menu of six tabs. The tabs read as one
sentence, left to right: **Film · Kind · Audience · Format · Style · Stages**. Each tab answers one
clause: which film, what kind, for whom, where it is shown, how it looks, and where the line stands.

| Tab | Clause | What it holds |
| --- | --- | --- |
| **Film** | Which film | A new film, or one card for each open film |
| **Kind** | What | Intro film, promo, explainer, tutorial, feature, reel from a video, video script, all versions |
| **Audience** | For whom | The audience and the version (market and language, such as `sd-ar`) |
| **Format** | Where | Platform, ratio, length, resolution, frame rate |
| **Style** | How | The look, the voice, the captions, the music |
| **Stages** | The line | The 14 stage cards, each with its lock and its gate |

The menu is data, not code. It lives in `departments/<dept>/settings.json`, so a choice can change
without a new app. A department that has this file gets the gear. Today only Video has one, and only
Video has a Stages tab, because only Video has a ledger.

**What one choice carries.** Every option in the menu is a small record:

| Field | What it is |
| --- | --- |
| `label` | The name on the button, in English and Arabic |
| `say` | The words the option adds to the sentence above the box |
| `sets` | Formula slots it fills (the `9:16` option sets `format` to `vertical 9:16, mobile`) |
| `line` | The phrase it adds to the formula's one-line `settings` slot (`look mixed`) |
| `keywords` | Kun keywords it stands for, such as `blender` or `shoot`. Each must exist in the vocabulary or be a skill |
| `tools` | The tools it calls on, by id from `stages.json` |

Options on the **Kind** tab carry three more: `formula` (the formula the kind starts), `when`
(`new` for a new film, `film` for an open one) and `workflow` (the keyword workflow it belongs to).

**A choice is defined once, and names the stage that owns it.** The choice `ratio` is written once,
in `settings.json`, with `"stage": "request"`. The Format tab shows it, and the request stage's
card shows the same choice. They are two views of one decision. `look` belongs to the visual stage,
`voice` and `music` to audio, `captions` to edit, `resolution` and `fps` to render.

**Tap and type are one path.** The menu does not build a prompt on its own. It asks one zero-token
command, `compose`, which turns the picks into a formula, its slot values and a sentence. The
sentence is written from the same words the switch (`match`) listens for. It contains the formula's
own trigger phrase (`Intro film` is a trigger of `video.film.plan`), so typing the sentence by hand
lands on the same formula. This is the real answer for the default picks:

```bash
node .claude/scripts/station.mjs match "Intro film · school owners · Sudan Arabic · Facebook 9:16 · 2:00 · real screens + 3D · stock voice" --dept video --repo hogwarts --json
```

```json
{
  "id": "video.film.plan",
  "confidence": 0.9,
  "dept": null,
  "set": {}
}
```

`settings` reads the menu for a department:

```bash
node .claude/scripts/station.mjs settings --dept video --repo hogwarts --json
```

It returns `{ dept, lang, project, tabs, sentence }`. A tab with `keys` becomes `groups`, one for
each key, and each group has its question, its `stage`, its `default`, its `current` value and its
`options`. A tab with `"source": "ledger"` (Film and Stages) is passed through; the app fills it from
`produce`. With `--project <film>`, `current` is the film's locked value, and the default otherwise.
This is the `ratio` group of the Format tab, trimmed to its English text:

(`set` is trimmed to the slots that differ from the first answer.) The Kind choice `reel` picked
another formula, `video.reel.footage`. The ratio changed the `format` slot. `missing` names the one
slot a person must still give, a source video.

**The reserved slot `new`.** `compose` adds `new: "1"` to a request for a new film. It is not a
slot of any formula. It tells `fill` to skip the formula's `redirects`. Without it, the New film
request would be handed over to the open film's stage formula (`video.film.plan` becomes
`video.stage.research` while a film is open) and the film would be worked on with no plan.

**With a film.** `compose --project <film>` only offers the Kind options marked `when: "film"`
(today, All versions), and there is no default: `formula` is `null` until one is chosen.

**Lint.** `station.mjs lint` checks the menu. It fails when a choice names a formula that does not
exist, a `sets` key that is not a slot of that formula, or a keyword that is in neither the
vocabulary nor the skills.

## Stages, specs and locks

Three words first. A **spec** is one stage's decisions written down: what will be made, with which
tool, from which inputs, into which files. A **lock** is a spec recorded in the film's ledger, with
who locked it, when, and a hash of the file. The **plan** is all 14 locked specs compiled into one
ordered list, and the run executes from it.

A lock freezes a decision before work. A gate approves a result after it. They are different, and
the agent still never approves.

**The table of the line.** `departments/video/stages.json` is the one table of the 14 stages and the
tool ladder. It carries the same keys, order and files as produce's own stage list, and `station.mjs
lint` fails if they drift apart.

| # | Stage | Folder | Deliverable | Gate | Spec drafted by | Choices it owns |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | request | `01-brief` | `request.json` | none | script | kind, audience, version, platform, ratio, length |
| 2 | research | `02-research` | `product-research.md` | none | script | none |
| 3 | brief | `01-brief` | `creative-brief.md` | none | agent | none |
| 4 | script | `03-script` | `script.md` | script | agent | structure |
| 5 | storyboard | `04-storyboard` | `shot-list.json` | none | agent | none |
| 6 | assets | `05-assets` | `asset-manifest.json` | none | script | stills |
| 7 | visual | `06-production` | `visual-manifest.json` | look | agent | look, threed |
| 8 | audio | `07-audio` | `audio-package.json` | none | script | voice, music |
| 9 | edit | `06-production/editing` | `edit-project.json` | none | script | captions, editor |
| 10 | render | `08-render` | `masters/master.mp4` | none | script | resolution, fps |
| 11 | qa | `09-quality` | `qa-report.md` | none | script | none |
| 12 | approval | none | none | version | script | none |
| 13 | cdn | none | none | none | script | none |
| 14 | publish | `10-publishing` | `publishing-record.md` | publish | script | none |

"Spec drafted by" says who writes the spec when a stage is opened. `script` means the standard
choices only: no model runs. `agent` means the video agent, read-only, for a stage that needs
writing or judgement. The four gates are unchanged: script, look, version and publish.

**The tool ladder.** The same file lists every tool and, for each kind of piece, the rungs from the
cheapest. The plan picks the first rung that is ready. A tool marked `staged` is listed with its price
and is never used until a `/decide` entry switches it on. The ladder is shown on the
[Video pipeline](/docs/pipeline#who-makes-what) page.

tool and the questions the app asks. It needs a film. For a film that has all 14 stages locked and
`look` changed to `captures`, this is the real answer (the questions are trimmed to their English
labels, the film's folder is written with `~`):

Each question is one owned choice that has two to four options, and the option that holds the
current value comes first. An owned choice with more than four options is not a question; it gets a
summary line that ends with `(change it in the <Tab> tab)`. The real answer also carries the film,
`label`, `done`, `tool_label`, `lane`, the spec's path and link, and the deliverable's path and link.
The commands that write a lock are on the [Produce](/docs/produce#lock-the-line) page.

**The formula that runs a locked plan.** `video.film.continue` now has two redirects, tried in order.
When every stage is locked it hands over to `video.film.run`, which executes the plan from the next
stage that is not done to the next human gate. Otherwise it hands over to the formula of the film's
stage, as before. With the throwaway film all 14 locked, the real answer to
`fill video.film.continue` was `video.film.run`; after `produce unlock … cdn` it was
`video.stage.research`. Each piece `video.film.run` hands out is briefed by a filled order formula:

| Formula | Makes |
| --- | --- |
| `video.order.still` | One still with Nano Banana in the Gemini app seat |
| `video.order.clip` | One generated clip. Its free rung is a person in the Gemini app seat |
| `video.order.motion` | One HyperFrames piece: a title card, a counter, a price card |
| `video.spec.stage` | Not an order. The read-only discussion of one stage's spec |

**Two blocks an agent turn may end with.** Besides `kun-questions`, the Video prompt
(`departments/video/prompt.md`) defines two fenced blocks, each the last thing in a turn and JSON
only. `kun-plan` ends the film plan: the film, all 14 stages with their decisions and tool, and the
cost. The app draws it as a plan card. `kun-spec` ends a stage discussion: one stage, its decisions
and its tool. The Lock button records it, and the agent never writes the spec file itself.

## Fill and match

**A tap fills.** When you tap an option, the app runs `station.mjs fill` with the option's formula
and the values the board attached to it. The script fills every slot from files and from the state
of the work, and the finished prompt appears in the box at once. No model runs and nothing is sent.
The formula's route is set silently at the same moment.

Continue production shows the redirect at work. Its formula, `video.film.continue`, looks at the
open film's stage and hands over to that stage's formula. Today the film is at the visual stage, so
the tap fills `video.stage.visual`.

**The sparkle button matches first.** When you type your own words and press the sparkle button,
the app first runs `station.mjs match`. This is the switch. It answers with a formula, a confidence
between 0 and 0.99, and a `set`: the values it could read out of your words. With a formula and a
confidence of 0.6 or more, the app fills that formula exactly as a tap does, handing the `set` to
`fill`. No model runs.

**Typing matches too, without the button.** Since 2026-11-22 the composer runs the same switch on
its own: when you stop typing for a quarter of a second and the box holds three words or more, it
asks `match`. A formula that clears the bar shows as a quiet chip above the box, for example
`⇥ Tab · Intro film · Balqalam · 9:16`, with up to three values the switch already read from your
words. **Tab** fills that formula, exactly as a tap or the sparkle button does; **Esc** dismisses the
chip and records a dismissal for the board's scoring; **Enter** sends your words as typed. When no
formula fits but a skill's trigger words do, the chip offers the skill instead (`⇥ Tab · /edit`).
Typing `/` opens a menu of this department's formulas, then its pack's skills, then the rest, the
way Claude Code lists its commands. Words the app picked up are underlined lightly.

The switch finds a formula in three ways, tried in this order:

1. **Another department's word.** When the text names another department and not your own, the
   switch matches it against that department's formulas and names the department in its answer. The
   app then moves the Department menu to it, without asking, and fills the formula there.
2. **A hand-over sentence.** "Give, hand, assign or send *a piece* to *a person*", or in Arabic
   اعط، سلّم or كلّف with لـ or إلى before the person. The words of the piece choose the work order:
   a scene is a Blender order, a script is a script order, a voice is a voiceover order. The answer
   carries the person as `to` and the piece itself.
3. **Trigger phrases.** Each formula lists phrases in English and in Arabic under `triggers`. The
   longest phrase found in your text wins.

A text that names another department, typed in Video:

```bash
node .claude/scripts/station.mjs match "sales quote a school for 48 students" --dept video --json
```

```json
{
  "id": "sales.quote.school",
  "confidence": 0.99,
  "dept": "sales",
  "set": {}
}
```

The `set` is empty here: the switch finds the formula and does not read the number out of the
sentence. After the fill, the number of students and the school's record id stay in the box as
unfilled slots for you to write. A request that fits a trigger phrase is simpler still:
«فيديو تعريفي لهوغورتس السودان» returns `video.film.plan` with a confidence of 0.92. The hand-over
sentence is shown in the [worked example](#a-worked-example-the-classroom-scene-goes-to-sedon)
below.

Only when nothing fits does a model run. That run is called *refine*: a short, read-only Claude run
on sonnet at medium effort that rewrites your words into the frame. Before it writes, it reads the
department's `CLAUDE.md` and everything the pack's `gather` list names. Step 4 of the
[Video pipeline](/docs/pipeline) page covers it.

**A slot that cannot be filled stays visible.** The script never leaves a blank silently. The slot
appears in the prompt as `[unfilled: scene]`, and the answer lists it under `missing`. In the app
you see the marker in the box and write the value yourself. A work order is stricter:
`produce order` refuses while anything is missing, and names the slot to pass with `--set`.

**How a film is pinned.** With no instruction, `fill` uses the first open film of the repo. To name
the film, pass `--project <film id>` (or `--set project=<film id>`). Every slot, every reference
link and every upload then comes from that film. An id that is not a known film is reported as
`missing: ["project"]`; the script never falls back to another film. The board pins for you:
Continue production carries the film's id, and `produce order` always pins its own film.

### The formula's question fields

The app no longer asks these questions locally. A tap fills the box, **Send** starts the chat, and the plan
run asks its own questions (see [pipeline](/docs/pipeline)). The fields below stay in the formulas as data,
and the zero-token command still answers them:

```bash
node .claude/scripts/station.mjs questions video.film.plan --dept video --repo hogwarts --json
```

It returns `{ id, intro: {en, ar} | null, questions: [{ slot, kind, q: {en, ar}, options: [{ value, label: {en, ar}, sets? }], default, current }] }`.
`intro` is the optional header line (`{{slot}}` placeholders filled like the body, so it names the brand).
`kind` is `choice` (a list), `ask` (free text, `options` empty) or `market` (one question, options from
`content/media/markets.json`, such as "Sudan · Arabic + English · 6.4 USD per student per year"). Slots
already in `--set`, and every context, map, json, argv, slug, value, ref and mul slot, are skipped.

A choice slot can be a combined question: `options: [{ value, label: {en, ar}, sets: { platform, format, length } }]`.
Picking one (`fill --set cut=<value>`) sets the other slots in `sets`; an explicit `--set` of one of those
slots still wins. Such a slot is only a selector, so it need not appear in the body. `intro` and `options`
are linted, and `order` lists the questions asked (for `video.film.plan`: audience, market, cut).

A formula tunes this in its header, all optional: `order` (the slots to ask, in order; `[]` asks
nothing), `q: {en, ar}` on a slot (the question; without it the slot name is humanised), `choice_ar`
(Arabic labels, one per choice), `model` (`opus`, `sonnet`, `haiku`) and `effort` (`low` to `xhigh`).
`fill --json` carries `model` and `effort` when the formula sets them. Lint rejects anything else;
the escalate model is never allowed.

The app does not call `questions`; `intro`, `q`, `order` and `choice_ar` are unused by it for now.

### Brand and exec slots

Two slot kinds carry what nobody should retype.

**`brand`** reads `content/media/brand-kit.json → production.<identity>`. The identity is the open film's own (`project.json → identity`), else the slot's brand, lowercased. One slot gives one field:

```json
"palette": { "brand": "{{brand}}", "field": "palette" }
```

| `field` | Fills | Example |
| --- | --- | --- |
| `logo` | The mark. A link in a work order, an absolute path elsewhere | `https://github.com/databayt/kun/blob/main/public/brands/hogwarts.png` |
| `fonts` | Names without the file extension | `Arabic headline thmanyah-serif-display-900 · Arabic body thmanyah-sans-500 · Latin Geist` |
| `palette` | Hex values by role | `canvas #faf9f5 · ink #141413 · accent #d97757 · …` |
| `voice` | The voice id and its note, never a `TODO` | `house-ar` |
| `direction` | The look in words | `trustworthy, modern, educational, product-focused` |

A draft identity is never guessed: the slot stays unfilled.

**`exec`** runs one fixed command and puts a short summary in the slot. The formula names an id and fills its parameters. It can never name a command. The ids are in `EXEC` in `station.mjs`; lint rejects any other.

| `exec` | Runs (no shell) | Parameters | Fills |
| --- | --- | --- | --- |
| `projects` | `produce.mjs list --json --repo <line>` | `line` | `hogwarts-intro-v001 (intro, in-production, next visual, sd-ar); …` or `none open` |
| `status` | `produce.mjs status <project> --json` | `project` | `<id>: 5/14 stages done (…); next <stage>` |

A parameter may hold only letters, digits, dot, dash and underscore. Anything else, or a missing one, runs nothing and the slot falls to its `default`.

A context slot can also read the company brief: `{"context": "company.why"}` returns the "Why this film" section of `departments/_shared/company.md`. `company-brief.mjs` writes that file (40 lines or fewer) from the Drive, the North Star, the sprint, the epics and the markets.

### English only

A pack can say `"lang": "en"`. The video pack does. `questions`, `board` and `fill` then return English in every `ar` field, and carry `lang: "en"`. The headers keep their `ar` strings for other departments.

### The video orders that carry the brand

| Formula | For | The brand slots give it |
| --- | --- | --- |
| `video.order.blender` | A Blender scene | Look, palette, fonts and logo. Camera, lens and light are set per shot from the shot list; every material takes a palette hex |
| `video.order.filmcraft` | Assembling the shot list over the source voiceover with the `filmcraft` MCP | The voiceover is the timing master; palette, fonts, logo and voice are filled |
| `video.order.image` | One picture from the ChatGPT seat | A prompt to paste: scene, style, palette hex, a 1088×1920 size, no text in the image. The seat is human: a person pastes it and saves `05-assets/images/<scene>.png` |

All three are work orders on sonnet at medium effort. The film plan takes an optional `source` slot, the path of a source video, and a `{{projects}}` line.

## Routes and lanes

A **route** is one way of running a request: plan it first, do it now, fan it out to several agents,
or do a quick small job. A **lane** is a row in the engine's table that fixes the model and the
effort for one kind of work. A route names a lane, and the lane decides the model: when a route
names a lane, the app takes the lane's model and effort over the route's own. The lanes are on the
[Lanes](/docs/lanes) page.

The four routes of the Video pack (`departments/video/pack.json → routes`):

| Route | Mode | Lane | Model · effort from the lane | Agent | Used for |
| --- | --- | --- | --- | --- | --- |
| `plan` (default) | plan, read-only | `judge` | opus · high | `video` | A new film: gather, ask, propose the journey. Changes nothing |
| `do` | auto | `work` | opus · medium | `video` | Work one stage, then stop at the gate |
| `workflow` | auto | `judge` | opus · high | `video` | Many versions at once: one Sonnet agent per version, each one verified |
| `quick` | auto | `research` | sonnet · low | none | Status, checks, lookups |

Routes are never shown in the app. A formula names its route in its header, and the app applies it
silently. Sales has three of the same routes (`plan`, `do`, `quick`) with the `sales` agent.

## Done means an issue

Three words first. A **gate** is a point where the work stops until a person says yes. Video has
four: script, look, version and publish. A **work order** is one request for one person with one
deliverable, written as a GitHub issue. A **receipt** is the comment on that issue that records what
was delivered.

"Done" means something different at each level, and each level has its own proof:

| Level | Done means | Proof |
| --- | --- | --- |
| A prompt | The right formula, filled, in the box | None. It lives in one window |
| Phase 1 | The plan is accepted and on GitHub: the film issue and its first work orders | The film issue's link |
| A work order | Its deliverable is submitted and the receipt is on the issue | The receipt comment |
| A gate | A person's approval is recorded on the film issue | The approval comment |
| The film | The CEO closes the film issue after publish | The closed issue |

The formula and the issue are not two things. **The body of a work order is the filled formula.**

**How a plan gets onto GitHub.** Under a finished plan the app shows one button, **Accept**. A typed
reply never starts work: it stays in plan mode and only answers or changes the plan. Accept moves to
the working route and sends one fixed English message. The formula that filled the box decides the
message, through its `record`:

| The formula's `record` | What the message asks the lead to do |
| --- | --- |
| `film` | Create the production if it does not exist yet, lock all 14 stages (`produce lock <ID> --all --plan <file>`), then its film issue (`produce issue <ID> --create`). For each piece the plan gives to another person, create its work order (`produce order <ID> <formula> --to <login> --create`). Reply with the links, then stop at the next gate |
| `issue` | Create the work order as an issue and reply with its link. Then stop |
| `none` | Carry out the first step, then stop at the next gate |

The formula that plans a film, `video.film.plan`, has `record: film`. So accepting a film plan is
what puts the film on GitHub, and phase 1 ends there. The `video` agent's own instructions cover
the moment: it prints each draft, reads it, and then creates it. A piece the agent does itself needs
no work order.

**The two kinds of issue**

| | Film issue | Work order |
| --- | --- | --- |
| How many | One for each film | As many as the film needs: one for each piece a person does |
| Shows | The brief, the versions with their links, the 14 stages as a checklist, the four gates, and a line for every work order | One request under the five headings |
| Labels | `dept:video`, `P2`, `film` | `dept:video`, `P2`, `for:<login>` |
| Held by | Nobody. It is the tracker | One person |
| Created by | `produce issue <ID> --create` | `produce order <ID> <formula> --to <login> --create` |
| Closed by | The CEO, after publish | The CEO, after the receipt is reviewed |

**Why a work order must travel.** A prompt that names a file on one Mac is useless on another
machine. A work order is read by a teammate on his own computer, so three things hold, and
`station.mjs lint` refuses a formula that breaks them:

- **Links, never paths.** Each reference in the film's folder becomes a link on the CDN,
  `https://cdn.databayt.org/work/<film>/ref/<file>`. The files are uploaded when the order is created.
- **Where to submit.** The Deliverable section names the place the result goes:
  `work/<film>/<issue number>/<file>`. An order whose result is words, not a file, says "Reply on
  this issue" instead.
- **Who it is for.** Every order has a `to` slot, and the Context section names both the person it
  is for and the person who ordered it.

### A worked example: the classroom scene goes to Sedon

The owner wants a teammate named Sedon to build the classroom scene of the Hogwarts intro film in
Blender.

**1. The sentence, then the command.** In the app the owner can simply type "give the classroom
scene to sedon" and press the sparkle button. The switch recognises a hand-over sentence. This is
the real answer:

```bash
node .claude/scripts/station.mjs match "give the classroom scene to sedon" --dept video --repo hogwarts --json
```

```json
{
  "id": "video.order.blender",
  "confidence": 0.92,
  "dept": null,
  "set": {
    "to": "sedon",
    "scene": "the classroom scene"
  }
}
```

The word "scene" chose the Blender order, and the sentence gave the person and the piece. The app
hands that `set` to `fill`, so the box holds the whole request for Sedon, ready to read and to
edit. Filling the box creates nothing.

Sending it does not start the work on your own machine. Because the formula records to an issue,
the app puts one fixed line in front of the text, "This is a work order for another person, not
work for you", and the video agent answers it by creating the issue and replying with the link.

What creates the issue, from the app or from a terminal, is one command, `produce order`. Without
`--create` it is a draft: it prints what would be made and changes nothing.

```bash
node ~/.claude/skills/produce/scripts/produce.mjs order hogwarts-intro-introduction-v001 \
  video.order.blender --to sedon --set scene="the classroom scene"
```

**2. What the issue will contain.** This is the real draft the command printed (the home folder is
shortened to `~`):

```text
DRAFT — nothing created, nothing uploaded.
film issue: (none yet — run `produce issue hogwarts-intro-introduction-v001 --create` before --create here)
title: Blender scene: the classroom scene — hogwarts intro — introduction
labels: dept:video, P2, for:sedon
references to upload (2):
  ~/media/_projects/hogwarts-intro-introduction-v001/03-script/script.md
    -> work/hogwarts-intro-introduction-v001/ref/03-script/script.md
    => https://cdn.databayt.org/work/hogwarts-intro-introduction-v001/ref/03-script/script.md
  ~/media/_projects/hogwarts-intro-introduction-v001/04-storyboard/shot-list.json
    -> work/hogwarts-intro-introduction-v001/ref/04-storyboard/shot-list.json
    => https://cdn.databayt.org/work/hogwarts-intro-introduction-v001/ref/04-storyboard/shot-list.json

## Task
Build the classroom scene in Blender from the shot list and render a preview, on your own machine.

## Context
- Work order: Blender scene, for sedon · ordered by Abdout
- Film: hogwarts-intro-introduction-v001 · hogwarts / Balqalam (the name the viewer sees)
- Piece: the classroom scene
- Format: vertical 9:16, 1080×1920, 30 fps

## References
- Script: https://cdn.databayt.org/work/hogwarts-intro-introduction-v001/ref/03-script/script.md
- Shot list: https://cdn.databayt.org/work/hogwarts-intro-introduction-v001/ref/04-storyboard/shot-list.json
- Brand kit: https://github.com/databayt/kun/blob/main/content/media/brand-kit.json
- Product look to match: ed.databayt.org

## Constraints
- Match the shot list for this scene: camera, timing, props and characters; phone and laptop screens show real captures only, supplied on the issue.
- Characters and places are illustrative: mark them so in the file's notes.
- Use the brand colours and type from the brand kit; never a licensed font that is not already in the kit.
- The order is one piece for one person. If something blocks you, say so on the issue instead of widening the work.
- Claims only from real captures; generated scenes are illustrative.
- No real student or parent data; brand name as the viewer sees it.
- Stop at every human gate (script · look/animatic · version · publish); never approve.

## Deliverable
- The .blend file `the-classroom-scene.blend` (packed textures, no absolute paths) and a preview render `the-classroom-scene-preview.mp4`.
- Note in the reply the Blender version and any add-on you used.
- Submit through the Kun app: open this order and press Submit with the files attached. The app uploads them to `work/hogwarts-intro-introduction-v001/<issue number>/<file>` on the CDN and posts the receipt on this issue.
- Reply on the issue with one line for the next person: what you did, what is left, anything they must know.

<!-- kun: repos=hogwarts; items=skill:blender; after=; film=hogwarts-intro-introduction-v001; formula=video.order.blender; weight=5 -->
```

The last three lines under Constraints were not in the formula. They are the Video department's
constraints, added by `fill`. The last line of all is the kun block; the app reads it and people do
not need to.

**3. The film issue comes first.** The second line of the draft says this film has no film issue
yet. `order --create` refuses until one exists. A film planned today gets its film issue when its
plan is accepted. This film was started before that, so the owner creates the issue once:
`produce issue hogwarts-intro-introduction-v001 --create`.

**4. Create the order.** The same command with `--create` uploads the two references to the CDN,
creates the issue in the film issue's repository with its three labels, adds a line for it under
"Work orders" on the film issue, and records it in the film's ledger.

**5. What Sedon sees.** The order reaches him in two places in his Kun app.

- **On the board.** The label `for:sedon` counts exactly like an issue assigned to him on GitHub.
  So the Video board puts the order in his Waiting place, as the option "Start my work order".
- **In the queue.** The app lists every open order labelled `for:` his login, whatever its
  department.

The board of a department shows only to a person whose profile has that department. If Video is
not in Sedon's profile, the queue is where he finds the order. The kun block says the order needs
`skill:blender`, so the app's readiness check offers to install it if it is missing. (Sedon needs a
profile in `machines/` before the app can show him anything; the example uses his name only.)

**6. Start.** Start claims the order. The issue gets the labels `holder:sedon` and
`status:in-progress`, and a chat opens with the request in it. Nobody else can start it: for anyone
else the claim is refused with "this order is for sedon".

**7. The work.** Sedon builds the scene in Blender on his own machine. The references open as links.

**8. Submit.** In the order's chat he writes one line about the work in the box. A line that starts
with `next:` is kept apart as the line for the next person. He presses **Submit** and chooses the
files, at most 20 at a time. The app asks kun for one short-lived upload link per file and sends
each file straight to `work/hogwarts-intro-introduction-v001/<issue number>/<file>` on the CDN. No
cloud key is ever on his computer. One line shows the progress, for example
"Uploading the-classroom-scene.blend (1/2)" with a percentage, then "Sending the receipt…", then
"Submitted. It is waiting for review."

**9. The receipt.** When every file is up, the app posts the receipt as a comment on the issue: the
summary, the links, a sha256 hash of each file, and the line for the next person. The issue moves
from `status:in-progress` to `status:review`. Only the person who holds the order can post it.

**10. Review and close.** The owner opens the links and reviews the work. Closing the issue is what
makes it done, and only the CEO closes. The next time the film issue is rewritten, the order's line
on it is ticked, and `produce status` lists Sedon among the film's contributors.

## The record

**What a receipt carries.** Every receipt is one comment with the same layout, so it can be read by
a person and counted by a script:

```text
<!-- kun:receipt -->
### Run receipt — <login>

Driver: <driver> · Model: <model> · Duration: <time>
Formula: <formula id> · Stage: <stage>

**Summary**
<what was done>

**Commits**
- none

**Artifacts**
- https://cdn.databayt.org/work/<film>/<issue number>/<file>

**Hashes (sha256)**
- <hash>  https://cdn.databayt.org/work/<film>/<issue number>/<file>

**Next**
<one line for the next person>

Ready for review (`status:review`). Only the CEO closes.
```

The first line is a marker the app looks for. The Formula line, the hashes and the Next line appear
only when they exist. A receipt posted by Submit in the app records the model as `human`.

**The kun block.** Every film issue and work order ends with one hidden line that machines read:

| Field | What it names | In the example |
| --- | --- | --- |
| `repos` | The repos the work needs | `hogwarts` |
| `items` | The skills or agents the machine must have installed | `skill:blender` |
| `after` | The issues that must be closed before this one can start | none |
| `film` | The film the order belongs to | `hogwarts-intro-introduction-v001` |
| `formula` | The formula the order was filled from | `video.order.blender` |
| `weight` | The formula's weight | `5` |
| `driver` | The agent program to use, when the order names one | not set |

**Only the CEO closes.** The labels say where an issue stands: `for:<login>` is who it was made for,
`holder:<login>` is who has claimed it, and `status:in-progress` and `status:review` are its state.
The holder and status labels are set by the machines, never by hand. Closed means done, and nothing
else does.

**Points come from the weight.** A formula's `weight` is copied into the kun block of every order
made from it, and the receipt names the formula. Points are the weight of the work, not the hours
spent on it. The calculation that turns points into a share is not built yet (see [Later](#later)).

**Issues are public.** An issue is written for anyone to read. A list price is fine, for example
the 24 SAR per student per year in `content/media/markets.json`. A commission or a share of revenue
is not. `produce order` checks the filled prompt for those words in English and Arabic; a draft
prints a warning, and `--create` refuses. A Sales issue names a school by its CRM record id only,
never by its name.

## Adding a department

Sales was the second department on this contract, and it is the example to copy.

1. **The pack**, `departments/<word>/pack.json`. It holds `lead` (the agent that talks to the
   person), `guard` (the check before anything goes out), `keywords` in English and Arabic,
   `constraints`, the `routes` with a `lane` each and a `defaultRoute`, `formula.en` (the frame,
   starting at `## Task`), and `quickActions` (the short list shown when the board cannot answer;
   an action with an `id` must be a formula). `health` and `gather` are optional.
2. **The ledger.** A ledger is where the department keeps its projects, stages and gates. Video's
   is produce, with 14 stages and four gates. Sales has none, and says so:
   `"ledger": { "adapter": "none", "gates": [], "stages": [] }`. A department with no ledger has no
   project slots and no gates, so its board scores from issues, sprint, drive, due and habit.
3. **A `formulas/` folder** beside the pack. The board needs at least one formula with
   `board: true` for each role: `waiting`, `next` and `start`.
4. **Check the formulas:** `node .claude/scripts/station.mjs lint --dept <word>`. It lists every
   error and exits with 1 when there is one.
5. **Check the words:** `node .claude/scripts/compile-words.mjs --check`. It lists any door skill,
   agent or spell that is missing or out of date. It is the check to run before the work is
   committed. Running it without `--check` writes the generated ones.

A Sales work order shows the other way to deliver. `sales.order.call` has `"submit": "comment"`:
its result is a reply on the issue, not a file on the CDN.

## Commands in one place

**The station** (`node .claude/scripts/station.mjs …`). Always pass the department with `--dept`;
without it the script uses `video`.

| Command | What it does |
| --- | --- |
| `board --dept <d> [--repo <r>] [--login <l>] [--health green\|orange\|red] --json` | Returns at most three options, each with its role, score and `why` |
| `fill <formula-id> --dept <d> [--repo <r>] [--login <l>] [--project <film>] [--set k=v]… --json` | Returns the filled prompt, its route, its `record`, what is `missing`, and the references to upload |
| `match "<text>" --dept <d> [--repo <r>] --json` | Returns the formula the text fits, a confidence, the values read out of the text (`set`), and the other department when the text names one (`dept`) |
| `lint [--dept <d>]` | Checks every formula; with no department it checks every department that has formulas |
| `settings --dept <d> [--repo <r>] [--project <film>] --json` | Returns the tabs of the settings menu, each choice with its options and its current value |
| `compose --dept <d> [--repo <r>] [--project <film>] [--set <choice>=<value>]… --json` | Turns menu picks into a formula, its slot values, the sentence, the keywords, the tools and what is `missing` |
| `stage <stage> --dept video --project <film> --json` | Returns one stage of a film: its lock, its current choices, its tool and the questions the app asks |
| `--test` | Runs the fixed test cases. No network |
| `--page` | Writes the formula matrix of every department at the end of this page |

**The issues** (`node ~/.claude/skills/produce/scripts/produce.mjs …`). Every command that writes to
GitHub prints a draft first; only `--create` writes.

| Command | What it does |
| --- | --- |
| `issue <ID>` | Prints the draft of the film issue |
| `issue <ID> --create` | Creates the film issue once. When it exists, `--create` or `--sync` rewrites its body from the current state |

## What we took from other products

| Pattern | Seen in | Evidence | Where it lands in Kun | State |
| --- | --- | --- | --- | --- |

| A skill is listed by one short line and loaded in full only when chosen | Hermes (`skills/AGENTS.md`: a 60-character description) | source | Door skills with a 60-character description; a formula's header is read for the board, its body only on fill | built |

| Fail closed when nobody can answer | DeepSeek Harness `user-approval` | source | Plan mode is read-only; anything that writes needs `--create` or Accept | built |
| One lead talks to the person; named single-job workers do the work | Grok Bot (primary and specialists); DeepSeek Harness (named children, depth limit) | docs and source | The department's lead agent and its sub-agents | built |

The evidence is of four kinds. The rows for Hermes, DeepSeek Harness and free-claude-code come from
reading their source code. The rows for Higgsfield's API, Dots, Grok Bot and Claude Duet come from
the makers' own documents and help pages. The last two rows come from an observation made on
2026-11-22 in the owner's own signed-in Higgsfield session, by reading the page's code. The row
about how often Duet checks comes from coverage, not from the maker, and the sources disagree.
Muse's help pages did not load, so Muse appears only where its public pages say something. Two rows
have no outside evidence at all: ranking suggestions from a person's own state, and recording work
as GitHub issues. Those are our own design.

The five rows about shots and stills come from the makers' own documents, read on 2026-11-23. The
exact labels in the Flow and Sora prompt boxes were not verified: no official page shows them, and
nothing in Kun depends on them.

Claude Duet could not be observed: the account's pages showed no Duet surface by the routes tried,
so nothing was learned about how it lists tasks. Whether choosing a Higgsfield preset rewrites the
prompt box also stayed unanswered, because nothing was clicked.

## Later

These are understood and not built.

- **The operations room.** One list of everything that waits for a yes, across all departments.
- **The share calculation.** Turning the points on closed issues into each member's share.
- **Native AskUserQuestion.** The plan run asks through a `kun-questions` block today. An Agent SDK
  helper could receive `AskUserQuestion` and `ExitPlanMode` directly and drop the block.
- **free-claude-code as a local engine.** It could run the cheaper lanes on a teammate's machine,
  under three conditions. It is licensed AGPL-3.0, so it runs as its own program and its code is
  never copied into Kun. Prompts leave to third-party providers, so no CRM, student or customer data
  goes through it. It is measured before any lane depends on it.
