# Interconnection

How the whole system holds together: the **kun engine**, the **machine fleet**, the **Hermes gateway**, the **self-hosted CRM**, and the four surfaces you touch Claude from (terminal, chat, Cowork, phone).

> **The core insight: nothing talks machine-to-machine.** Every machine talks to a small set of shared cloud services — GitHub, Slack, Vercel, the CRM — and those services *are* the interconnection. No VPN, no port-forwarding, no server administration for the team.

## How work flows — SENSE → THINK → ACT → LEARN

You talk to **one door** — a Claude Code session, from the terminal, the Desktop Code tab, the
iPhone (Remote Control), or Slack (Hermes). The session splits the work; you don't. Every surface
and every loop follows the same four beats:

```
 SENSE ─────────────► THINK ─────────────► ACT ─────────────► LEARN ─┐
 aware.mjs            resolve.mjs           lanes + ledger          improve.mjs
 one snapshot of      names → repos and     main session, agents,   findings from the
 everything, 0 tokens blocks; dispatch      Workflows, loops        runs → SAFE fixes,
                      table picks lane,     (kun-claude.sh logs     DECIDE → one issue,
                      model, effort         tokens + cost)          measured before/after
   ▲                                                                       │
   └─────────────────────── the Monday routine closes the loop ◄───────────┘
```

### Talk to kun — plain words, few of them

| You say | What happens |
|---|---|
| "mkan listing is broken" | the router names `~/mkan` (its own CLAUDE.md applies), the session works there |
| "fix the admission form" (from a kun session) | one hint: the hogwarts `admission` block — and that `seek` also uses the word — the session picks by context |
| "fix the admission form" (inside hogwarts) | the full block protocol: read the block's records first, update them + its docs + the issue after |
| "status" / "حالة" on Slack | Hermes pastes `~/.claude/state/aware.md` — zero Claude tokens |
| "deploy balqalam" on Slack | Hermes hands it to Claude Code with `auto`; the router picks hogwarts; the thread stays there |
| "sync self" / "improve yourself" | `/sync self`: apply safe fixes, refresh the Engine decisions issue, apply what you approved |
| "yes 9ac6e654" on the Engine decisions issue | approves that row; the next `sync self` (or Monday) applies it and measures the result |

### SENSE — awareness of everything happening

`node ~/kun/.claude/scripts/aware.mjs` takes one zero-token snapshot: the machine (disk + its
24 h trend, swap, sessions, Remote Control), every scheduled job (`runs.sh`, Hermes cron), spend
(the headless ledger plus every transcript's usage — fresh tokens vs cache reads, per surface,
average context per turn), the engine (heartbeat, sync tiers, bench age, findings, decisions past
review), the queue (reports, issues by priority, Cowork handoffs), main CI per repo, Hermes, WIP,
and which sessions are active now. Where you read it:

| Surface | How |
|---|---|
| Every session start | a ≤5-line brief, silent when green (`session-aware.sh`, ~30 ms) |
| iPhone / Slack | alerts (below) and "status" via Hermes |
| Cowork | reads `~/.claude/state/aware.md` through the filesystem |
| GitHub | each machine's #133 health report carries an awareness block |

**Alerts are transitions, not nags**: a condition must hold on two refreshes in a row, is sent
once, clears when it goes away, and at most 6 go out a day. At the Mac → a banner; away → this
machine's `~/.claude/.kun-notify` target (Abdout: his Slack DM). Alerted: disk under 10 GB or
falling 5 GB/day, a job turning red, Hermes or Remote Control down, a failed main CI, commits
unpushed for 12 h. Shown but never alerted: spend, sync, bench, dirty files.

| Alert | Owner (the one place it comes from) |
|---|---|
| jobs, disk, CI, Hermes/RC down, unpushed | `aware.mjs` (owner Mac: every 30 min) |
| report-an-issue queue | the SessionStart reports hook (from aware's cache) |
| domains, mail | the `domains` GitHub Action → `domains` issues |
| engine findings | `improve.mjs` → the Engine decisions issue |
| weekly plan | the Monday routine → one message |

### THINK — the router and the dispatch table

`resolve.mjs` turns names into places before the model guesses: a **block of the current repo**
gets the block protocol; **another repo by name** (hogwarts, mkan, souq, shifa — and aliases like
balqalam, بالقلم, mkan.sd) gets a one-line pointer; a **curated global block** (admission,
attendance, timetable, parent-portal, …) gets a one-line hint from any session. Generic words
(docs, table, finance, grades, listings) never route across repos; `kun` and `codebase` never
route bare. Policy: `engine.json → resolver`; registry: `.claude/memory/repositories.json`.

Then the session picks a lane — **the dispatch table** (`engine.json → delegation`):

| Work | Lane | Model · effort |
|---|---|---|
| Q&A, small edits, deciding | the main session | Opus 5.5 · session effort |
| Look up across many files | an Explore subagent | sonnet · low |
| Mechanical edit, formatting, git | haiku agents (git, comment, icon, …) | haiku · low |
| Build to a known pattern | build agents | sonnet · medium |
| Review, verify, judge | opus specialists, Workflow verify stages | opus · high |
| Fan out with verification | a Workflow (qa, handover, textbook, scrape, …) — every stage names its model and effort (lint-enforced) | per stage |
| Long or recurring work | a loop through `kun-claude.sh` (ledgered; lean when it needs no skills or MCP) | per job |
| An errand in Abdout's name | `/behalf`, then Cowork | — |
| An easy one-file task, off the Max pool | Antigravity (`a`) | Gemini |
| Another running session | `ListAgents` → `SendMessage` (Code ↔ Code, any machine) | — |

### ACT — every run leaves a receipt

Headless Claude runs go through `~/.claude/bin/kun-claude.sh`: same args, same output, plus one
ledger line (job, model, effort, tokens, cost, turns, duration) and an optional daily cap.
`bash ~/.claude/scripts/runs.sh --spend` totals it per job. Measured on 2026-11-01: a one-word
headless reply from `~/kun` cost 67.9K tokens with the context hooks, 61.1K without them (they
now stay silent headless), and 39.5K in lean mode (no MCP, no skill listing).

### LEARN — kun improves itself

`improve.mjs` (zero tokens, daily in the heartbeat) reads kun's own evidence — the ledger, the
awareness history, the router log, transcripts, lint, health, bench-retire — and files findings
with stable ids: **SAFE** (mechanical — applied automatically), **DECIDE** (changes behaviour,
cost or a fleet surface — one row each on the rolling **Engine decisions** issue, approved with
`yes <id>`), **TRACK** (context for the weekly plan). After a change, the detector either stops
firing (**verified**) or comes back (**regressed**) — measured, never assumed.

**The Monday routine** (`scripts/captain/weekly.sh`, Mondays 08:00 on the owner Mac): sense →
detect → one ledgered Opus run that applies `sync self`, syncs the anthropic tier only when a new
Claude Code release exists, and writes the week's plan to `.claude/memory/weekly/` — never the
1.3M-token bench, never a 36-day catch-up. Abdout gets one message.

### The commands, in one place

```bash
node ~/kun/.claude/scripts/aware.mjs              # everything happening, now
bash ~/.claude/scripts/runs.sh                    # every scheduled job: ok / red / stale
bash ~/.claude/scripts/runs.sh --spend            # headless spend per job, last 7 days
node ~/kun/.claude/scripts/resolve.mjs "<words>"  # where would these words route?
node ~/kun/.claude/scripts/improve.mjs            # what kun would improve, and why
bash ~/kun/scripts/captain/weekly.sh --status     # the Monday routine
```

## Layer 1 — Kun engine: a repo, not a service

Kun is the shared brain, and it propagates through **git**. The `.claude/` tree (skills, agents, rules, vocabulary, memory, hooks) *is* the engine; any machine that clones `databayt/kun` and runs [onboarding](/docs/onboarding) becomes an engine node.

```
databayt/kun (.claude/ config)
     │
     │  clone + daily pull (maintain heartbeat)
     ├────────────────► Abdout's Mac ──┐
     └────────────────► 6 teammate  ───┤  heartbeat status
                        machines       │
                                       ▼
                        Dashboard issue (kun#133)
```

- **Propagation** = `git pull`. There is no config server.
- **The maintain heartbeat** runs daily on every machine: pull → refresh → health-check → report status to the shared dashboard issue. Fleet health is visible without touching anyone's laptop.
- **Drift detection**: `.claude/engine.json` holds the expected counts; `/health` flags divergence.

## Layer 2 — The machine fleet

| Machine | Runs | Hosts services? |
| ------- | ---- | --------------- |
| **Host machine** (Abdout's Mac) | Claude Code (`c` lane) · Cowork · Hermes gateway (`h` lane) | Yes — Hermes |
| **Teammate machines** (× 6) | Claude Code + kun config clone | No — consume everything by URL |
| **Phone** (iPhone) | Claude app (Code tab, push) · Slack · GitHub | No — a remote control for the host Mac |

Only the host machine runs a long-lived service (Hermes). Everyone else consumes the shared fabric with a browser and a terminal.

## Layer 3 — Hermes: one binary, two pipes

Hermes ([hermes-agent](https://github.com/nousresearch/hermes-agent), the `h` lane) runs on the host machine and is **a relay, never the LLM** — Claude writes every word. It carries two unrelated flows:

```
PIPE 1 — inbound gateway (talk to the machine)
  Phone / Slack app ──DM──► Slack ──Socket Mode──► Hermes ──► machine's agent
                                    (outbound WS,             acts, replies,
                                     no public endpoint)      pushes proactively

PIPE 2 — social egress (the machine talks out)
  kun.databayt.org Social Hub ──HERMES_API_URL──► Hermes ──► Slack / X channels
        (on Vercel)           ──direct Bot/Graph API──────► Telegram + Facebook
                                                             (no Hermes needed)
```

> **Hermes-Slack ≠ Slack MCP.** Hermes lets *you* talk to your machine from Slack; the Slack MCP lets *Claude* post to Slack as a tool. Both coexist — neither replaces the other. Full wiring: [Hermes](/docs/hermes).

Telegram and Facebook deliberately bypass Hermes — the site calls their official APIs directly over HTTPS, which works from Vercel with no local gateway.

## Layer 4 — CRM: the business memory

Self-hosted from `databayt/crm`, served at four product subdomains. It never runs on teammate machines — everyone reaches it by browser with **one identity** (`<id>@databayt.org`, the same login as Slack).

| Workspace | URL | Pipeline |
| --------- | --- | -------- |
| Hogwarts | hogwarts.crm.databayt.org | Schools, sponsors, pilots |
| Mkan | mkan.databayt.org | Property/rental leads |
| Sijillee | sijillee.crm.databayt.org | Pre-launch prospects |
| Moallimee | moallimee.crm.databayt.org | Pre-launch prospects |

Business state flows back into the engine through a human-paced loop: Aseel keeps pipelines clean → the captain reads headline numbers weekly into `kun/.claude/memory/pipeline.json` → the engine's weekly planning sees real pipeline data. Details: [CRM](/docs/crm).

## Layer 5 — The four surfaces

| Surface | Where | Role | Connects via |
| ------- | ----- | ---- | ------------ |
| **Claude Code** | Terminal on every machine; the Desktop app's Code tab on the host | The *doing* lane — builds, ships, fixes | git/GitHub, MCPs, hooks, skills |
| **Remote Control** | Every host session, plus the always-on `kun-rc` server ("Mac · kun") | Drive running Mac sessions, or start new ones, from the phone | The Claude app's Code tab · claude.ai/code |
| **Cloud sessions** | The Code tab, claude.ai/code, routines (`/schedule`) | Work that must keep going with the Mac off | GitHub repos |
| **Claude chat** | claude.ai + mobile app | Thinking anywhere; the cheapest surface | — |
| **Cowork** | Claude Desktop | The *planning* lane — two shells (cloud + on-device), Dispatch, computer use; no Claude Code hooks | Shares `~/.claude/` by filesystem MCP; hands off via `bridge.md` + issues |
| **Phone** | iPhone | Receive, steer, start | Built-in push (held while you're at the Mac) · `SendUserFile` · private Artifacts · Code tab · Slack → Hermes |

The host Mac keeps this layer alive with `.claude/scripts/devices.sh`: a presence service (pushes wait while you're at the Mac), the `kun-rc` Remote Control server in tmux, and a session-start brief that speaks up when disk, swap or the server need attention. `bash ~/.claude/scripts/devices.sh --status` shows all of it; policy lives in `engine.json` → `devices`.

> **Cowork and Code never share conversations.** They share only files (`~/.claude/`), GitHub issues, and push notifications. The bridge is deliberately file-shaped — `~/.claude/bridge.md` for short handoffs — so either side picks up where the other left off at session start. Details: [Cowork](/docs/cowork).

| Bus | Carries |
| --- | ------- |
| **GitHub** | Code, kun config, work queue (issues), heartbeat dashboard — the durable bus everything settles onto |

## Reuse it — run this map for your own team

Everything above is configuration, not product. To stand up the same topology:

1. **Fork [`databayt/kun`](https://github.com/databayt/kun)** — the `.claude/` tree is the engine. Strip `docs/` and `.claude/memory/` of databayt-specific state; keep the structure.
2. **Pick your fabric** — a GitHub org (code + issues + config bus), a Slack workspace (human bus), a Vercel team (deploy plane). Free tiers cover a small team.
3. **Run onboarding on each machine** — clone, `setup.sh`, and every laptop becomes an engine node. See [Onboarding](/docs/onboarding).
4. **Optional lanes** — wire [Hermes](/docs/hermes) on one always-on machine if you want chat-to-machine access; self-host a CRM if you have a sales pipeline. Neither is required for the core loop.
5. **Adopt the heartbeat** — a daily pull + health report per machine keeps a distributed team's config from drifting. The scripts live in `.claude/scripts/`.

What's genuinely databayt-specific: the vocabulary (our keywords), the memory (our clients), the docs (our decisions). What's generic and reusable: the layer model, the git-propagated config, the bus discipline, the heartbeat, the Cowork bridge, the Hermes two-pipe pattern.

## Contribute to it

**Team** — work directly on `main`, no branches, no PRs (see the workflow rule in `.claude/rules/github-workflow.md`). Docs live in `content/docs/`; config in `.claude/`. Commit small and often; deploys run through the `deploy` skill. When you change the topology (new service, new lane, new bus), update **this page** in the same commit — the map is only useful while it's true.

**Community** — the repos are public under [github.com/databayt](https://github.com/databayt):

- **Questions and ideas** → open an issue on `databayt/kun`.
- **Fixes and additions** → fork and open a PR; a maintainer reviews and lands it on `main` (the no-PR rule is internal discipline, not a door closed to outside contributions).
- **Reusing the engine** → you don't need permission; it's open source. If you adapt the map for your team, an issue telling us what you changed makes the pattern better for everyone.
